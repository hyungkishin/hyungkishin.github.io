JVM 메모리를 그릴 때 먼저 스레드를 두 개 놓아 봤다. 같은 영수증 객체에서 첫 번째 스레드는 수수료를 읽고 두 번째 스레드는 영수증을 출력한다고 하자. 영수증은 한 장인데 실행 중인 메서드와 명령의 위치는 스레드마다 다르다.

그래서 힙과 메서드 영역은 한 번만 그리고, JVM 스택과 프로그램 카운터(PC)는 스레드마다 하나씩 그렸다.

여기서 영수증을 만든 메서드가 먼저 끝났다고 하자. 스택에서 그 메서드가 빠졌는데도 바깥에서는 어떻게 수수료를 읽을까?

JVM의 런타임 데이터 영역

자바 메서드를 실행할 때 PC는 그 스레드가 실행 중인 JVM 명령을 가리킨다. JVM 스택에는 아직 끝나지 않은 메서드 호출의 기록이 남아 있다. 네이티브 메서드를 실행하는 동안의 PC 값은 JVM 명세에서 정하지 않는다. 구현에 따라 네이티브 호출에 별도의 스택을 쓸 수도 있다.

두 스레드가 함께 읽는 영수증 인스턴스는 힙에 있다. 배열도 힙에 둔다. 그 영수증 클래스에 어떤 필드와 메서드가 있는지, 메서드를 실행하려면 어떤 바이트코드가 필요한지는 메서드 영역에 저장한다.

메서드 영역에는 클래스나 인터페이스마다 런타임 상수 풀이 하나씩 있다. 다른 클래스의 메서드를 호출할 때 필요한 클래스 이름, 메서드 이름과 타입도 호출하는 쪽의 상수 풀에 들어간다. JVM 명세 2.5절 런타임 데이터 영역

그림에서는 힙과 메서드 영역을 역할에 따라 따로 그렸다. JVM 명세를 보면 메서드 영역도 논리적으로 힙의 일부다. 이 영역에서 GC를 하거나 빈 공간을 모을지는 구현에 맡긴다. JVM 명세 2.5.4절 메서드 영역

이제 JVM에 힙을 32MiB만 주면 프로세스 전체도 그만큼만 쓸까? -Xmx는 힙의 상한이다. HotSpot은 클래스 메타데이터 대부분을 네이티브 메모리의 메타스페이스에 저장하고, JIT가 만든 기계어도 별도의 코드 캐시에 둔다. 직접 버퍼의 데이터도 자바 힙 밖에 놓이는 경우가 있다. 프로세스 전체의 사용량을 볼 때는 이 공간들도 함께 센다. HotSpot의 클래스 메타데이터, HotSpot 코드 캐시, Java 직접 버퍼

스택 프레임 하나가 생기고 사라질 때

한 메서드가 자기 자신을 다시 호출해도 두 호출의 인자는 서로 덮어쓰지 않는다. 호출할 때마다 JVM 스택에 프레임을 하나씩 만들기 때문이다. 각 프레임에는 인자와 지역 변수를 담는 슬롯, 계산 중인 값을 올려놓는 피연산자 스택, 현재 클래스의 런타임 상수 풀을 가리키는 참조가 있다. 재귀가 너무 깊어져 허용된 스택 크기를 넘기면 StackOverflowError가 난다. JVM 명세 2.6절 프레임

스택이라는 말이 두 번 나왔다. 정수를 더하는 동안 어느 스택이 바뀔까? iadd를 실행하면 한 프레임 안에서 3과 4가 빠지고 7이 올라온다. 덧셈 명령에 피연산자의 위치를 따로 적을 필요가 없다. JVM을 스택 머신이라고 부르는 이유다. 그동안 호출 스택에는 같은 프레임이 그대로 있다. JVM 명세 2.6.2절 피연산자 스택

record Box(int value) {}

static Box make(int value) {
    Box box = new Box(value);
    return box;
}

Box result = make(7)을 호출하면 정수 7이 두 군데에 들어간다. 하나는 make가 인자로 받은 지역 변수 value, 또 하나는 힙에 만든 Box 안의 필드다. 지역 변수 box에 담은 것은 그 객체를 가리키는 참조다.

return box에서 호출자에게 건네는 값도 그 참조다. make 프레임이 사라진 다음에도 호출자는 자기 쪽에 남은 result로 아까 그 Box의 필드를 읽는다.

new가 공간을 얻고 생성자가 값을 채우는 순서

소스에는 new Box(value) 한 줄뿐인데 바이트코드 그림에는 new와 invokespecial이 따로 보인다. Box 클래스가 아직 초기화되지 않았다면 JVM은 클래스부터 초기화한다. 그다음 새 인스턴스의 공간을 확보하고 필드를 기본값으로 준비한다. 여기까지 int 필드의 값은 0이다. 생성자가 실행돼야 비로소 7이 들어간다. JVM 명세의 new 명령

그림에서 dup 다음 행을 보면 U가 두 개다. 객체를 두 번 만든 걸까? new는 한 번만 실행됐다. dup이 복사한 건 그 객체를 가리키는 참조다.

invokespecial은 참조 하나와 정수 7을 꺼내 생성자를 호출한다. 생성자가 끝나면 남은 참조는 초기화된 객체를 가리킨다. astore_1으로 지역 변수 box에 이 참조를 저장하고, aload_1으로 다시 꺼낸다. areturn에서 호출자가 받는 값이 바로 이 참조다. 앞 글에서 본 피연산자 스택

HotSpot 객체에는 필드 외에도 타입과 잠금 상태 등을 기록하는 헤더가 있다. Box 하나를 만들 때 필요한 공간에는 이 헤더와 정렬에 필요한 여백까지 들어간다. HotSpot 객체 헤더

힙을 함께 쓰면 두 스레드가 객체 하나를 만들 때마다 같은 빈자리를 두고 경쟁할까? HotSpot은 공유 힙의 일부를 스레드별 할당 버퍼(TLAB)로 미리 나눠 줄 수 있다. 자기 버퍼에 자리가 남아 있으면 그 안에서 다음 할당 위치만 객체 크기만큼 옮긴다.

버퍼를 나눈 기준은 누가 할당하느냐다. 그곳에 만든 영수증도 다른 스레드에 참조를 넘기면 그 스레드도 같은 영수증을 읽는다. OpenJDK 25의 TLAB 할당 코드

JIT가 필요한 필드 값만으로 계산을 끝낼 수 있으면 실제 할당을 생략하기도 한다. 바이트코드의 new 개수만 세서는 힙 사용량을 계산하기 어렵다. HotSpot의 탈출 분석

GC가 살아 있는 객체를 찾고 공간을 회수하는 과정

make는 끝났지만 호출자의 result로 Box에 닿을 수 있었다. GC도 실행 중인 스레드가 계속 사용할 참조 같은 GC 루트에서 출발해 객체 사이의 연결을 따라간다. 일반 참조를 따라 루트에서 닿는 객체는 살아 있다. 도중에 다른 객체의 필드나 배열을 거쳐도 마찬가지다.

목록에서 영수증 하나를 지웠다고 하자. 그림 속 목록에서 출발하는 화살표 하나가 지워진다. 그런데 호출자의 지역 변수에도 그 영수증이 남아 있다면? 루트에서 출발할 길이 하나 더 있으니 여전히 회수 대상이 아니다. 이렇게 루트에서 객체까지 길이 남아 있는지를 도달 가능성이라고 한다.

두 객체가 서로 참조해도 루트에서 어느 쪽에도 닿을 수 없으면 둘 다 회수 대상이다. 반대로 이미 기한이 지난 항목도 살아 있는 목록에 계속 두면 GC를 몇 번을 해도 남는다. Java의 도달 가능성 정의

플러그인을 내렸는데도 클래스가 남는 경우를 생각해 보자. 플러그인 객체를 모두 지워도 애플리케이션이 그 클래스를 정의한 로더를 보관하고 있으면 그 로더가 정의한 일반 클래스는 남는다. 로더 자체가 회수 대상이 되면 클래스도 언로딩 대상이 된다. 실제로 언제 언로드할지는 JVM에 달렸다. 부트스트랩 로더가 정의한 클래스는 제외된다. Java 언어 명세 12.7절 클래스와 인터페이스의 언로딩

실제로 빈 공간을 만드는 방식은 수집기마다 다르다. G1은 힙을 같은 크기의 리전(region)으로 나눈다. 작은 새 객체는 보통 Eden 리전에 들어간다. 젊은 세대 수집에서 살아남은 객체는 Survivor나 Old 리전으로 옮긴다. 일반적인 대피(evacuation) 과정에서는 선택한 리전의 살아 있는 객체를 다른 리전으로 복사하고 참조를 고친다. 대피를 마친 리전은 통째로 다시 할당에 쓸 수 있다. JDK 25 G1의 힙 배치와 회수 과정

짧은 실험으로 확인한 객체의 수명

Box를 수수료 100원이 찍힌 영수증으로 바꿔서 실행했다. saveForLater 안에서 영수증을 만들고 그 참조를 static 필드 saved에 넣었다. 메서드 밖에서 saved.feeWon()을 찍어 보니 100이 나왔다.

그다음에는 saved = null로 마지막 강한 참조를 끊었다. 영수증을 확인하려고 강한 참조를 하나 더 남겨 두면 그 참조 때문에 영수증이 살아남는다. 미리 걸어 둔 WeakReference가 큐에 들어오는지만 최대 2초 기다렸다. 실행할 Java 소스, 바이트코드 발췌

같은 코드, 다른 실행 조건 2초 안에 큐에서 약한 참조를 받았나?
G1에서 System.gc() 요청 허용 새 JVM에서 다섯 번 모두 받았다.
-XX:+DisableExplicitGC로 명시적 요청 무시 한 번 실행했다. 기다리는 동안 통지는 없었다.

둘 다 Temurin 25.0.4.1에 힙은 32MiB였다. 두 실행에서 똑같이 saved = null을 실행했다. 그런데 한쪽에서는 큐에 통지가 왔고 다른 쪽에서는 2초 동안 아무것도 받지 못했다.

마지막 강한 참조가 사라진 줄은 코드에서 짚을 수 있다. 큐에서 통지를 받은 시점에는 GC가 약한 참조를 처리했다는 것도 안다. 영수증이 차지했던 자리에 다음 객체를 언제 할당했는지는 이 출력에 없다. 기본 실행 출력, G1 로그, 대조 실행 명령과 출력

네이버 D2의 2011년 JVM 그림에는 PermGen이 나온다. 그런데 영수증 예제를 실행한 JDK 25의 HotSpot에서는 그 이름을 찾을 수 없다. 지금은 클래스 메타데이터 대부분을 메타스페이스에 둔다. D2의 JVM Internal

Pratik T의 예제를 보면서 “그럼 int는 스택에 있나?”라는 질문을 다시 생각해 봤다. 위의 make(7)에서 메서드 인자도 int이고 Box 안의 필드도 int다. 인자로 받은 값은 프레임에, 인스턴스 필드는 객체 안에 그려야 두 개의 7이 구분된다. 이 그림은 코드의 참조 관계를 나타낸다. JIT가 이 할당을 없앴다면 실제 힙에는 Box가 생기지 않는다. Understanding JVM Memory Allocation, HotSpot의 탈출 분석
