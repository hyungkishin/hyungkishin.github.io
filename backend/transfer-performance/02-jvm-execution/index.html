자바 메서드의 실행 시간을 비교할 때는 JVM이 어떤 실행 경로를 사용했는지도 맞춰야 한다. 같은 .class 파일을 실행해도 처음 호출할 때와 반복해서 호출한 뒤의 기계어가 같다는 보장은 없다. HotSpot은 실행 중 모은 정보를 사용해 자주 실행되는 코드를 컴파일한다. 비교하는 두 코드의 실행 단계가 다르면 측정값에는 코드 변경의 효과와 JVM의 준비 비용이 섞인다.

이전 글에서 정한 측정 구간과 부하 조건에 JVM 실행 조건을 더해야 하는 이유다. 서버 기동 직후의 응답 지연과 충분히 실행한 뒤의 처리량은 각각 따로 관찰할 대상이다. 정상 상태의 계산 비용을 비교하면서 첫 호출만 재면 준비 비용이 섞인다. 기동 직후의 문제를 조사하면서 준비 구간을 전부 버리면 필요한 현상을 놓친다.

아래 실행 예제는 OpenJDK 25.0.4.1에서 컴파일과 출력을 확인한 결과다. 바이트코드의 의미는 Java SE 25 명세를 기준으로 설명한다. JIT와 메모리 최적화는 HotSpot의 구현에 관한 설명이다. 예제에서 해당 최적화가 발생했다고 측정한 결과는 없다.

소스, 바이트코드, 기계어의 역할

javac가 만드는 .class 파일에는 JVM이 실행할 바이트코드가 들어간다. 바이트코드는 특정 CPU의 명령어와 독립적인 형식이다. JVM 명세는 각 명령의 동작과 실행에 필요한 자료 구조를 정한다. 이를 인터프리트할지 기계어로 번역할지는 구현에 맡긴다. JVM 명세 2장

일반적인 HotSpot 실행에서는 인터프리터와 JIT 컴파일러가 함께 쓰인다. JIT는 실행 시점에 바이트코드를 해당 CPU가 실행할 기계어로 컴파일한다. 자주 호출되는 메서드나 반복되는 루프가 컴파일 대상이 될 수 있다. 생성한 기계어는 code cache에 저장한다. 소스 파일을 다시 작성하거나 .class 파일을 덮어써서 실행을 바꾸는 과정은 아니다.

단계별 컴파일인 tiered compilation은 프로파일을 수집하는 컴파일 코드와 더 많은 최적화를 적용하는 코드를 함께 사용한다. C1과 C2라는 이름은 HotSpot의 두 JIT 컴파일러를 가리킨다. 모든 메서드가 동일한 순서와 시점에 두 컴파일러를 거치는 것은 아니다. 컴파일 대상과 시점은 실행 횟수, 수집한 정보, JVM 설정 등에 영향을 받는다. HotSpot의 단계별 컴파일과 code cache

이 구조에서 warmup은 측정 전에 정해진 시간만 기다리는 행동으로 끝나지 않는다. 비교할 코드 경로를 실제 입력으로 실행해야 그 경로의 프로파일이 쌓인다. 준비 구간에 사용한 입력 타입이나 분기가 측정 구간과 다르면, 측정을 시작한 뒤에도 컴파일과 실행 경로의 변화가 이어질 수 있다.

반복문을 컴파일한 실제 바이트코드

피연산자 스택의 동작은 짧은 반복문으로 확인할 수 있다. 다음 코드는 Hello World를 열 번 출력한다. 콘솔 출력 시간이 포함되므로 이 예제를 정수 증가 연산의 성능 측정에 사용하지는 않는다.

public class HelloLoop {
    public static void main(String[] args) {
        for (int i = 0; i < 10; i++) {
            System.out.println("Hello World");
        }
    }
}

실행 환경은 Temurin OpenJDK 25.0.4.1+1-LTS, 컴파일러는 javac 25.0.4.1이다. 아래 명령을 실행했고 컴파일, 프로그램 실행, 바이트코드 출력이 모두 정상 종료했다. 프로그램의 표준 출력에는 같은 문장이 정확히 열 줄 있었다. 소스, JDK 버전, 표준 출력, javap 출력을 함께 보관했다.

javac -g HelloLoop.java
java HelloLoop
javap -c -l HelloLoop

javap -c는 클래스 파일의 바이트코드를 출력한다. -l은 줄 번호와 지역변수 테이블을 출력한다. 컴파일할 때 사용한 -g는 지역변수 이름을 포함한 디버깅 정보를 남긴다. 아래는 실제 출력에서 main의 명령 부분을 발췌하고 주석을 줄인 것이다. javap 명령 문서

 0: iconst_0
 1: istore_1
 2: iload_1
 3: bipush        10
 5: if_icmpge     22
 8: getstatic     #7    // System.out
11: ldc           #13   // String Hello World
13: invokevirtual #15   // PrintStream.println:(String)V
16: iinc          1, 1
19: goto          2
22: return

왼쪽 숫자는 메서드의 바이트코드 시작점을 기준으로 한 바이트 오프셋이다. 명령 길이가 다르므로 3 다음은 5이고 5 다음은 8이다. #7, #13, #15는 이 클래스 파일의 상수 풀 인덱스다. 다른 컴파일 결과에서는 같은 필드와 메서드가 다른 번호로 표시될 수 있다.

이 출력에서는 지역변수 슬롯 0이 args, 슬롯 1이 i다. main이 static 메서드라서 첫 인자를 슬롯 0부터 받는다. 인스턴스 메서드의 슬롯 0에는 호출 대상 객체의 참조인 this가 들어간다. 지역변수 슬롯 번호와 명령의 바이트 오프셋은 서로 다른 번호다.

피연산자 스택에서 이동하는 값

JVM의 스택 기반 명령은 연산에 필요한 값을 피연산자 스택에 넣고 꺼내 사용한다. iconst_0은 정수 0을 넣는다. 이어지는 istore_1은 그 값을 꺼내 지역변수 슬롯 1에 저장한다. 이 시점의 i는 0이고 피연산자 스택은 비어 있다.

iload_1은 슬롯 1의 값을 스택에 복사한다. bipush 10이 정수 10을 넣으면 스택에는 아래부터 [0, 10]이 놓인다. if_icmpge는 두 값을 꺼내 먼저 들어간 값이 나중 값 이상인지 비교한다. 첫 반복의 0 >= 10은 거짓이므로 다음 명령을 실행한다. i가 10이 되면 오프셋 22로 이동해 return을 실행한다.

그림에서 iinc 1, 1은 별도의 경로를 사용한다. 피연산자 스택을 거치지 않고 지역변수 슬롯 1의 정숫값에 1을 더한다. 스택 기반이라는 분류가 모든 명령에 push와 pop이 필요하다는 뜻은 아니다. JVM 명령 정의: iload, if_icmp, iinc

출력 명령에서는 객체의 참조가 움직인다. getstatic은 System.out 정적 필드의 값을 읽어 스택에 넣는다. 이어지는 ldc는 Hello World 문자열 객체의 참조를 넣는다. invokevirtual은 호출 대상인 PrintStream 참조와 문자열 인자를 꺼내 println을 호출한다. 이 메서드의 반환 타입은 void이므로 호출이 정상 종료한 뒤 반환값을 스택에 넣지 않는다.

이 과정을 설명할 때 문자열 객체 전체가 스택으로 복사된다고 해석하면 안 된다. 피연산자 스택에 놓이는 것은 해당 객체를 가리키는 참조다. getstatic의 역할을 필드 이름의 해석으로만 설명하는 것도 부족하다. 필드를 확인한 다음 그 필드에 저장된 값을 스택에 넣는 동작까지 포함한다. JVM 명령 정의: getstatic, ldc, invokevirtual

호출 스택과 프레임 안의 스택

JVM 스택에는 메서드 호출의 프레임이 쌓인다. 각 프레임은 지역변수 배열과 피연산자 스택을 포함한다. main이 println을 호출하는 동안 main의 지역변수 i와 호출받은 메서드의 지역변수는 각자의 프레임에 속한다. 호출이 끝나면 호출한 쪽의 실행으로 돌아간다. 프레임과 지역변수의 정의

호출 스택은 어느 메서드로 돌아갈지를 포함한 호출 상태를 다룬다. 피연산자 스택은 현재 메서드의 명령에 필요한 값을 다룬다. 힙은 객체와 배열을 저장하는 실행 영역이다. 지역변수나 피연산자 스택에 객체 참조가 들어 있다는 사실만으로 그 객체의 저장 위치가 스택이라고 결론 내릴 수 없다.

이 설명은 JVM이 보장하는 실행 의미다. JIT가 인라이닝한 호출에는 독립된 기계어 호출과 물리적인 프레임이 남지 않을 수 있다. 바이트코드의 스택 연산도 기계어에서는 레지스터 연산으로 표현되거나 다른 연산과 합쳐질 수 있다. 바이트코드 명령 수를 세어 실제 CPU 명령 수나 실행 시간을 계산할 수 없는 이유다. HotSpot의 컴파일 과정에는 레지스터 할당과 기계어 생성이 포함된다. HotSpot 컴파일러 구조

실행 프로파일에 의존하는 JIT

인라이닝은 호출할 메서드의 내용을 호출 지점에 포함하는 최적화다. 호출과 반환에 필요한 작업을 줄이는 것과 함께, 호출 경계 너머의 계산을 한꺼번에 분석할 여지를 만든다. 소스에서 메서드를 읽기 좋은 단위로 나눴다고 해서 모든 호출이 실행 시점의 비용으로 그대로 남는 것은 아니다.

가령 수수료 계산 인터페이스를 호출하는 지점에서 실제로 들어오는 객체가 한 구현 타입에 집중된다고 가정하자. HotSpot은 실행 중 수집한 타입 정보 등을 사용해 해당 구현을 인라이닝할 수 있다. 이때 특정 타입만 나타난다는 전제는 프로그램 전체의 영구적인 계약이 아니다. 이후 입력이나 로딩된 클래스가 바뀌면 전제가 성립하지 않을 수 있다.

HotSpot은 가드나 의존 관계를 사용해 이런 전제를 확인한다. 전제를 더 이상 사용할 수 없으면 해당 코드의 실행을 deoptimization으로 전환할 수 있다. 필요한 실행 상태를 복원하고 인터프리터 등의 경로에서 이어서 실행한다. 이후 수집한 정보로 다시 컴파일할 수도 있다. 프로그램의 의미를 유지하면서 실행 전략을 바꾸는 과정이다. HotSpot의 인라이닝과 동적 deoptimization

그림은 가능한 전환 순서를 보여 준다. 시간 간격이나 처리 속도는 실측값이 아니다. 새 타입을 만날 때의 전환 여부는 생성한 코드와 가드에 달려 있다. 특정 메서드의 인라이닝 여부와 컴파일 시점을 판정하려면 해당 실행의 컴파일 로그나 프로파일이 필요하다.

JIT 자체도 CPU와 메모리를 사용한다. 시작 직후의 CPU 사용량에는 애플리케이션 계산과 컴파일 작업이 함께 들어갈 수 있다. 같은 부하를 주더라도 한쪽 JVM만 이미 해당 경로를 충분히 실행했다면 비교 조건이 어긋난다. 단 한 번의 실행 시간에서 나타난 차이를 코드 변경의 효과로 분리하기 어렵다.

객체 할당과 풀링에 붙는 조건

소스에 new가 있다고 해서 그 위치의 힙 할당이 기계어에도 그대로 남는 것은 아니다. HotSpot의 escape analysis는 객체가 분석한 범위 밖으로 노출되는지를 판단한다. 조건이 맞으면 scalar replacement로 객체의 필드를 개별 값처럼 다루고 객체 할당을 제거할 수 있다. Oracle의 Java 25 문서는 이를 객체를 힙에서 스택으로 통째로 옮기는 최적화와 구분한다. HotSpot의 escape analysis

인라이닝을 거친 분석 범위 밖으로 객체가 실제 노출되거나 분석이 충분하지 않으면 할당이 남을 수 있다. 소스에서 메서드가 객체를 반환하더라도 호출자에 인라인된 뒤에는 할당 제거 대상이 될 수 있다. 탈출하지 않는 객체라고 해서 모든 경우에 할당 제거가 적용되는 것도 아니다. 소스만 읽고 “이 객체는 스택에 생성된다”거나 “이 new는 비용이 없다”고 단정할 근거는 부족하다. 해당 JDK와 실행 경로에서 할당량을 확인해야 한다.

작은 임시 객체를 줄이려고 전역 풀을 도입하면 다른 비용이 생긴다. 풀에서 찾고 반환하는 작업, 재사용 전 상태 초기화, 스레드 사이의 동기화를 설계해야 한다. 풀의 참조가 객체를 오래 유지할 수도 있다. 반대로 DB 연결처럼 생성 과정에 외부 자원 확보가 필요한 대상은 재사용 비용과 생성 비용의 관계가 다르다. 객체 수만 같다고 같은 풀링 전략을 적용할 수는 없다. Oracle의 객체 풀링 비용 논의

풀링 문서는 오래된 JVM을 대상으로 쓰였으므로 당시 GC 설정과 수치를 현재 환경에 옮겨 쓰지 않는다. 여기서 가져올 판단 기준은 생성 비용을 줄이는 대신 어떤 유지 비용을 추가하는지 비교하는 것이다. 실제 애플리케이션에서는 요청당 할당량, GC, 유지되는 객체 크기와 지연을 함께 확인해야 풀의 효과를 판정할 수 있다.

측정 코드도 컴파일 대상이다

계산 결과를 사용하지 않는 반복문은 측정하려던 계산 자체를 잃을 수 있다. 컴파일러가 외부에서 관찰할 효과가 없는 계산이라고 판단하면 dead code elimination으로 제거하기 때문이다. 반복 횟수를 늘려도 없어진 계산이 돌아오지는 않는다. 이때 잰 시간은 소스에 적힌 작업의 비용과 다를 수 있다.

JMH는 JVM에서 작은 코드 구간을 측정하기 위한 벤치마크 도구다. 공식 예제는 계산 결과를 벤치마크 메서드의 반환값으로 넘기거나 Blackhole로 소비하는 방식을 보여 준다. 출력으로 결과를 소비하면 콘솔 I/O의 비용이 섞인다. 실제 출력 성능을 측정하는 경우가 아니라면 계산과 출력을 분리해야 한다. JMH의 dead code elimination 예제

결과를 반환하더라도 입력이 컴파일 시점에 충분히 예측 가능하면 constant folding이 개입한다. 매번 계산하려던 결과를 미리 구하거나 반복문 밖으로 옮길 여지가 생긴다. JMH의 공식 예제는 @State 객체의 변경 가능한 필드에서 입력을 읽는 방법을 설명한다. 업무 입력이 바뀌는 계산을 측정하면서 리터럴 하나만 넣으면 실제 요청과 다른 코드를 측정할 수 있다. JMH의 constant folding 예제

같은 JVM에서 A와 B를 차례로 실행하는 것도 실행 순서의 영향을 받는다. 앞선 측정이 남긴 타입 프로파일이 다음 측정의 컴파일에 영향을 줄 수 있기 때문이다. JMH의 fork는 별도 JVM 프로세스에서 실행해 이 영향을 줄인다. warmup은 각 프로세스 안에서 코드 경로를 준비하는 역할이므로 fork와 같은 설정이 아니다. JMH의 프로파일 혼합과 fork 예제

측정 횟수와 warmup 횟수에 모든 코드에 통하는 정답은 없다. iteration별 결과가 계속 움직이는지, fork 사이의 차이가 큰지, 입력이 실제 호출 형태를 반영하는지를 확인해야 한다. JMH 결과도 정해진 조건에서의 작은 코드 구간을 설명한다. 그 수치를 HTTP 요청 전체의 지연으로 바꾸려면 DB 대기와 네트워크를 포함한 별도 측정이 필요하다.

문자열 연결 팁에도 컴파일 조건이 있다

문자열의 +를 발견할 때마다 StringBuilder로 바꾸는 규칙은 컴파일러의 현재 동작을 생략한다. JDK 9의 JEP 280은 문자열 연결을 invokedynamic으로 표현하는 방향을 도입했다. StringConcatFactory는 알려진 인자의 타입과 개수 등을 바탕으로 연결 동작을 구성한다. 소스의 + 개수와 중간 객체의 개수가 일대일로 대응한다고 가정할 수 없다. StringConcatFactory 문서, JEP 280 도입에 관한 OpenJDK 릴리스 문서

이 변화가 반복문에서 문자열을 누적하는 모든 형태의 비용을 없애지는 않는다. 길어지는 문자열에 매번 내용을 덧붙이는 코드는 누적 길이에 따른 할당과 복사 비용을 확인해야 한다. 이런 용도에서는 하나의 StringBuilder에 순차적으로 추가하는 형태가 비교 대상이 된다. 짧은 연결식 하나와 긴 누적 반복문은 같은 측정 대상으로 취급하지 않는다.

JVM 버전만 확인하는 것으로도 부족하다. 같은 런타임에서 실행해도 어떤 컴파일러와 target으로 .class를 만들었는지에 따라 바이트코드 형태가 달라질 수 있다. 문자열 연결의 비용을 비교한다면 생성한 바이트코드를 먼저 확인한다. 같은 입력 길이와 문자 구성으로 할당량과 실행 시간을 함께 측정한다. Kotlin 코드에도 Java 컴파일러의 결과를 그대로 가정하지 않고 해당 Kotlin 컴파일 결과를 확인한다.

실행 조건을 기록한 뒤 업무 경로로 돌아가기

성능 비교에는 JDK 배포판과 버전, JVM 옵션, CPU·메모리 제한을 남긴다. 시작 직후를 측정했는지, warmup 뒤를 측정했는지와 입력 분포도 함께 적는다. 이 조건들이 달라지면 동일한 소스 코드에서도 생성한 기계어와 실제 대기 시간이 달라질 수 있다.

본문에서 실행으로 확인한 범위는 HelloLoop의 컴파일 결과, 지역변수 슬롯과 열 번의 출력이다. JIT 인라이닝 비율, 할당 제거 여부, StringBuilder 전환의 성능 차이는 측정하지 않았다. 이 값들은 설명한 최적화가 존재한다는 사실에서 자동으로 따라오지 않는다.

작은 계산의 실행 구조를 확인한 뒤에는 요청이 완료되는 조건으로 범위를 넓혀야 한다. 다음 글에서는 송금 요청이 성공했다는 응답과 실제 잔액 변경의 관계를 다룬다. 메서드 하나의 실행 시간을 줄여도 업무 결과가 늦게 확정되거나 중복 반영된다면, 사용자가 기다리는 요청을 올바르게 처리했다고 볼 수 없다.
