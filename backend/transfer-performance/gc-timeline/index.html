세대별 수집이 기대하는 세 가지 분포

세대별 수집은 객체의 나이를 보고 어느 공간부터 비울지 고른다. 갓 생긴 객체가 일찍 죽는다면 젊은 공간을 먼저 비워 적은 복사로 자리를 많이 얻을 수 있다. 이때 드는 비용은 오래 살아남은 객체의 수명과 세대를 건너는 참조의 수에도 달려 있다. 수집기가 기대하는 분포는 다음 세 가지다.

가설 무엇을 기대하나 수집 방식에 미치는 영향
약한 세대 가설 새로 만든 객체 중 많은 수가 일찍 죽는다. 젊은 세대를 자주 회수하면 살아서 복사해야 할 양이 작다.
강한 세대 가설 오래 살아남은 객체일수록 다음 구간도 살아남을 가능성이 높다. 여러 차례 수집을 견딘 객체를 오래된 세대로 옮겨 반복 복사를 줄인다.
세대 간 참조 가설 세대를 가로지르는 참조가 같은 세대 안의 참조보다 적은 편이다. 오래된 쪽에서 젊은 쪽을 가리킬 가능성이 있는 위치를 기록하면, 젊은 세대만 수집할 때 검색 범위를 좁힐 수 있다.

세 가지 모두 프로그램이 만드는 객체와 참조의 분포에 관한 가정이다. 오래 보관한 캐시 전체를 한꺼번에 지우는 프로그램에서는 비슷한 나이의 객체가 같은 시점에 대거 죽는다. 실제 프로그램에서 추적한 오래된 객체의 수명 분포도 강한 세대 가설을 따르는 경우와 벗어나는 경우가 모두 있었다. 객체 수명 분포를 측정한 연구 · 세대별 수집과 기억 집합의 초기 실측

참조 배열의 여러 칸을 덮어쓰는 경우는 앞 편의 System.arraycopy 실험에서 보았다. 세 번째 가설에는 이런 쓰기를 추적하는 비용이 따른다. 오래된 배열의 한 칸에 새 객체를 넣으면, 젊은 세대를 수집할 때 그 칸에서 오는 참조도 찾아야 한다. G1의 쓰기 장벽은 참조를 저장할 때 변경한 필드가 속한 메모리 구간인 카드를 기록한다. 수집할 때는 기억 집합(remembered set)으로 바깥에서 들어오는 참조를 찾는다. 오래된 배열을 자주 갱신하면 장벽과 카드 처리에 드는 일도 늘 수 있다. G1의 기억 집합 · OpenJDK의 카드 기록 경로

빈 공간을 모으는 비용과 멈추는 시간

살아 있는 객체를 표시한 뒤 죽은 객체의 자리를 돌려주는 방식을 mark-sweep이라고 한다. 빈 공간이 4칸씩 두 곳에 흩어져 있으면 합계가 8칸이어도 6칸짜리 객체 하나를 넣을 수 없다. 이런 단편화를 줄이는 mark-compact는 살아 있는 객체를 모아 빈 공간을 이어 붙인다. 객체를 옮길 위치를 구하고 그 객체를 가리키는 참조도 고쳐야 한다. OpenJDK Serial Full GC의 새 주소 계산, 참조 수정, 객체 이동

그 일을 하는 동안 요청을 계속 처리할 수 있을까? Serial GC는 애플리케이션을 멈추고 GC 스레드 하나가 일한다. Parallel GC도 애플리케이션을 멈추지만 여러 GC 스레드가 일을 나눠 처리량을 높인다. 예전 HotSpot의 CMS는 오래된 세대의 표시 작업 대부분과 쓸기 작업을 애플리케이션과 동시에 진행했다. 초기 표시와 재표시에는 정지가 남았고, 평소 객체를 제자리에 두기 때문에 흩어진 빈 공간에 다음 할당이 들어가지 않을 수도 있었다. JDK 25의 Serial과 Parallel GC · JDK 8의 CMS 수집 과정과 할당 실패 조건

G1은 한 번의 정지에서 객체를 옮길 범위를 리전 단위로 고른다. 살아 있는 객체가 적은 리전을 먼저 비우면 적게 복사하고도 같은 크기의 리전을 통째로 얻는다. 그 이득을 얻으려면 옮겨 갈 빈 공간이 필요하고 다른 리전에서 들어오는 참조도 추적해야 한다. JDK 25의 G1 대피와 리전 선택 기준

젊은 리전을 비울 때와 오래된 리전을 고를 때

G1은 힙을 일정한 크기의 리전으로 나눈다. Young GC에서는 애플리케이션 스레드를 잠시 멈추고 젊은 리전에서 살아 있는 객체를 빈 Survivor 또는 Old 리전으로 복사한다. 참조를 새 위치에 맞추고 대피(evacuation)에 성공한 리전은 통째로 다시 쓸 수 있다. 여러 GC 작업 스레드가 병렬로 복사해도 이 구간에 애플리케이션은 멈춘다. OpenJDK 25.0.4.1의 G1YoungCollector::collect

앞 글의 도달 가능성을 기준으로 오래된 리전에 살아 있는 객체가 얼마나 남았는지 세어 보자. G1은 Concurrent Start라는 Young 정지에서 마킹을 시작할 준비한다. 이어 애플리케이션이 실행되는 동안 객체 사이의 참조를 따라간다. Remark에서는 다시 멈춰 남은 표시 작업을 마무리한다. 이후 기억 집합 재구성 등을 거쳐 Cleanup 정지에서 다음 회수 단계를 준비한다. 표시는 무엇이 살아 있는지 조사하는 일이고, 대피는 선택한 리전에서 그 객체를 옮기는 일이다. OpenJDK의 마킹 주기 실행 순서 · Remark에서 마무리하는 작업

회수할 오래된 리전이 남으면 Mixed GC에서 젊은 리전과 선택한 오래된 리전을 함께 비운다. 한 번에 넣을 오래된 리전의 수에는 후보 수와 예상 정지 시간 예산이 영향을 준다. 로그에 Pause Young (Mixed)가 찍혔다면 젊은 세대만 비웠다고 읽을 수 없는 이유다. Mixed 진행 여부 · 수집할 오래된 리전을 고르는 코드

26.924ms부터 32.740ms까지의 G1 로그

Temurin 25.0.4.1의 96 MiB 힙에서 배열을 반복 할당하자 로그에 Concurrent Mark Cycle 2.899ms가 찍혔다. 이 시간 동안 애플리케이션은 얼마나 멈췄을까? 그림은 JVM 기동 후 첫 마킹 주기 주변만 확대한 것이다. 가로축은 실제 시각에 비례한다. 세로선의 속도만 늦췄다. 위쪽 띠는 마킹 주기 전체, 아래쪽 파란 막대는 각각의 애플리케이션 정지다.

26.924ms에 시작한 정지는 GC(6) Pause Young (Concurrent Start)다. 0.457ms 뒤 이 작업이 끝나고 GC(7) Concurrent Mark Cycle이 시작했다. 그 안에서 GC(8)과 GC(9)라는 별도의 Young GC가 끼어들었다. 같은 GC(7)에 속하는 Remark와 Cleanup 정지는 각각 0.091ms와 0.010ms였다. 주기 전체의 2.899ms를 정지 합계에 더하면 동시 작업까지 정지로 세고, 그 안에서 발생한 정지도 중복 계산한다. 해당 구간의 연속된 원본 로그

30.993ms에는 Prepare Mixed가 시작됐다. 실제 Mixed는 32.225ms에 시작한 GC(11)이다. 이 정지에서 힙 사용량이 75M에서 52M으로 줄었고 로그가 기록한 정지 길이는 0.515ms였다. 로그의 시작·종료 행을 출력한 시각과 내부 타이머로 잰 길이는 반올림과 기록 지점 때문에 마지막 자릿수가 다를 수 있다.

같은 양을 할당하고 힙만 두 배로 늘린 결과

실험 코드는 한 스레드에서 4 KiB 배열을 2,097,152번 만든다. 배열 데이터만 합해 8 GiB다. 최근 128개를 보관하고 네 개 중 하나는 길이 5,120의 순환 배열에도 남긴다. 새 항목이 이전 칸을 덮으면 오래된 참조가 끊긴다. 여덟 번 모두 마지막 배열들에서 계산한 체크섬은 1136000이었다. 실험 Java 소스

Apple M4 Pro에서 G1이 인식하는 프로세서 수를 4로 고정했다. JVM이 시작할 때부터 끝날 때까지 힙 크기를 48 MiB 또는 96 MiB로 유지했다. 각 조건을 새 JVM에서 네 번씩, 48·96·96·48 MiB 순서를 두 차례 반복했다. 아래 값은 각 조건의 실행별 중앙값이다. 처리량은 배열 수를 JVM 프로세스 실행 시간으로 나눈 값이다. 실행별 측정값

측정 항목 힙 48 MiB 힙 96 MiB
JVM 시작부터 종료까지 551.92 ms 423.87 ms
GC 정지 시간의 합 250.55 ms 173.12 ms
초당 처리한 배열 수 380만 개 495만 개
Full GC 횟수 5회 0회

힙을 48 MiB 더 주자 같은 할당 작업을 끝내는 시간이 짧아졌다. 48 MiB에서는 Full GC가 실행마다 3~6회 있었고 96 MiB에서는 네 번 모두 없었다. 반면 가장 길었던 단일 정지는 48 MiB의 네 실행을 통틀어 1.098ms, 96 MiB에서 5.347ms였다. 정지 시간의 합과 최장 정지는 서로 다른 질문에 답한다. 이 실험은 네트워크 요청을 보내지 않았으므로 어느 값도 요청 지연을 나타내지 않는다. 8회 전체 원본 GC 로그 ZIP

재현하려면 같은 디렉터리에 Java 소스와 아래 스크립트를 둔다. JDK 25의 java와 javac가 PATH에 있는 상태에서 실행하면, 빈 결과 디렉터리에 원본 로그 여덟 개와 CSV가 생긴다. 정지 합계는 [gc]의 Pause 종료 행에 기록된 길이만 더한 값이다. 동시 마킹이 사용한 CPU 시간과 운영체제 스케줄링에 따른 대기는 별도로 측정하지 않았다. 측정·집계 스크립트

수집기가 정지 밖으로 옮겨 온 일

JDK 9는 서버 구성의 기본 수집기를 G1으로 바꿨다. 긴 정지를 줄이기 위해 일부 추적을 애플리케이션과 겹치고, 한 번에 비우는 범위를 제한하는 선택이었다. JDK 11에서 실험 기능으로 등장해 JDK 15에서 정식 기능이 된 ZGC는 객체를 다른 위치로 옮기는 작업까지 애플리케이션과 동시에 진행한다. 객체에 접근할 때 쓰는 장벽이 이동 중에도 올바른 참조를 찾도록 돕는다. JDK 21의 Generational ZGC는 여기에 세대를 나눠 젊은 객체를 더 자주 수집할 수 있게 했다. JDK 9의 G1 기본화 · ZGC의 동시 이동 설계 · JDK 15 정식 기능 전환 · JDK 21의 세대별 ZGC

큰 배열 세 개가 리전 여섯 개를 차지한 이유

G1은 큰 객체(humongous object)를 오래된 세대의 연속된 리전에 배치한다. JDK 25 안내서는 대략 리전 절반부터 이 범주로 설명한다. 실험 버전의 HotSpot은 헤더·정렬을 포함한 객체 크기를 워드 단위로 계산해 절반 초과인지 검사한다. byte[]의 length는 데이터의 바이트 수이므로 객체 전체 크기와 차이가 있다. JDK 25의 큰 객체 할당 · 실험 버전의 크기 비교

리전 하나를 1 MiB로 고정하고 같은 크기의 배열 세 개를 살아 있게 한 뒤 GC를 요청했다. 배열 길이가 각각 500,000바이트인 실행에서는 로그의 Humongous regions가 0->0, 600,000바이트에서는 3->3, 1,100,000바이트에서는 6->6이었다. 마지막 경우에는 각 배열이 리전 두 개를 차지한다. 마지막 리전에 남은 공간은 그 객체가 회수될 때까지 다른 객체에 줄 수 없다. 할당 코드 · 세 JVM의 옵션과 로그

운영 로그에서는 먼저 -Xlog:gc*,gc+heap=info의 리전 크기, Humongous regions, Full GC의 원인과 회수 전후를 맞춰 본다. 큰 할당에는 연속 공간이 필요해 흩어진 빈 리전의 합계만으로 성공을 예측하기 어렵다. 리전 수만으로 단편화를 확정할 수도 없다. JFR 할당 표본에서 배열 타입·크기·호출 위치를 확인하고, 같은 부하에서 버퍼를 나누거나 리전 크기를 조정했을 때 여유 공간과 정지가 어떻게 변하는지 비교한다. 위 실험에서 확인한 것은 점유 리전 수다. 연속 리전 부족으로 인한 할당 실패는 발생하지 않았다. 큰 객체와 Full GC 진단

객체가 오래 남을 때 수집기를 다시 고르는 기준

96 MiB 힙에서 한 스레드가 4 KiB 배열 262,144개를 할당했다. 최근 32개만 보관하자 GC 직후 Old 리전 수의 최댓값은 3, Full GC는 0회였다. 최근 8,192개를 보관하자 최댓값이 96, Full GC가 16회였다. 나이 1인 생존 객체들의 바이트 합계도 한 번의 수집에서 기록된 최댓값이 214,152바이트에서 4,194,240바이트로 늘었다. 전체 할당량은 같았다. 오래된 리전 수에는 승격 이외의 요인도 반영되므로 이 수치를 그대로 초당 승격 바이트로 환산할 수는 없다. 참조를 유지하는 실험 코드 · 명령·로그와 집계 기준

서비스에서 같은 현상을 만나면 할당률과 gc+age=trace의 연령별 생존 바이트, 승격·Old 점유량 변화, 마킹을 마친 뒤의 생존 집합을 같은 시간축에 둔다. 정지 목표를 계속 넘기는 구간에는 대피 실패와 Full GC가 있었는지를 함께 본다. 재배포 때마다 클래스 메타데이터가 늘면 먼저 로더가 해제되는지도 확인한다. 정의 로더를 붙들었다가 놓는 실험

객체를 보관할 이유가 사라졌는데 계속 참조한다면 참조 수명부터 고친다. 유지가 필요한 데이터라면 운영의 할당률·생존 분포를 재현해 같은 CPU·메모리 예산과 요청 부하에서 G1과 후보 수집기를 비교한다. 짧은 꼬리 지연이 목표면 ZGC의 동시 작업이 애플리케이션의 CPU·메모리 여유를 얼마나 쓰는지, 처리량이 목표면 Parallel GC의 정지 시간이 허용 범위인지 본다. 선택 기준은 요청 p99·p99.9, 목표 처리량과 오류율이며 GC 정지 분포와 GC CPU는 차이의 원인을 설명한다. 위 실험은 수집기 간 우열을 측정한 결과가 아니다.
