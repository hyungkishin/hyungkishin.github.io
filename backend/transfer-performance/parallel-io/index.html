조회 A는 150ms, B는 300ms를 기다리도록 만들었다. 결과를 합치려면 두 응답이 다 필요하다. 그런데 B를 요청하는 데는 A의 응답이 필요 없다. 그렇다면 A부터 기다릴 이유가 있을까. 기다리는 시간만 놓고 보면 450ms짜리 일이 300ms 언저리에서 끝날 만하다. B에 보낼 토큰을 A에서 받아야 했다면 이 계산은 처음부터 성립하지 않는다.

순차로 473ms, 함께 보내면 312ms

루프백 HTTP 서버에 /a와 /b를 두고 150ms, 300ms 후에 각자 자기 경로를 돌려주게 했다. 같은 HttpClient를 써서 순서대로 호출한 뒤 플랫폼 스레드 두 개짜리 풀에 동시에 맡겨 봤다. 마지막으로 작업마다 가상 스레드를 하나씩 줬다. 매번 두 응답의 값이 맞는지 검사한 시점까지 시간을 쟀다.

다섯 번씩 잰 중앙값은 순서대로 473ms, 312ms, 312ms였다(Apple M4 Pro, macOS ARM64, JDK 25). 플랫폼 스레드 두 개만으로도 짧은 쪽 대기 시간이 긴 쪽에 거의 다 겹쳤다. 동시에 처리한 요청이 고작 두 건이니, 이 숫자로 고부하에서 어느 쪽 처리량이 높을지는 알 수 없다. HTTP 서버와 클라이언트 소스, 시도별 값과 실행 명령

두 조회를 시작하는 쪽을 포크(fork), 같은 요청에 속한 두 결과를 모으는 쪽을 조인(join)이라고 한다. 제출 순서대로 기다리면 A가 끝나기 전에 B의 실패를 알 수 없다. 여기서는 여러 실행기와 함께 쓸 수 있는 ExecutorCompletionService로 끝난 작업부터 꺼냈다. 응답에 경로 이름을 붙여 두면 B가 먼저 와도 결과를 뒤섞을 일이 없다.

어디에 실행 상태를 보관할까?

실행 방식 대기 중에 일어나는 일 선택할 상황
플랫폼 스레드 풀 HotSpot의 플랫폼 스레드는 보통 OS 스레드 하나에 대응한다. 동기 소켓 읽기에 걸린 작업자는 그동안 같은 풀의 다른 일을 맡을 수 없다. 동시에 진행할 작업이 적거나 CPU 연산이 중심일 때 작업자 수와 큐를 제한한다.
가상 스레드 JVM은 여러 가상 스레드를 플랫폼 스레드에 배정한다. 이때 가상 스레드를 실행하는 플랫폼 스레드를 캐리어 스레드(carrier thread)라고 한다. 지원되는 블로킹 I/O에서 실행을 중단하면 Java 호출 스택을 보존한 채 캐리어 스레드를 다른 작업에 쓸 수 있다. 동기 Java API를 쓰면서 많은 연결이 응답을 기다릴 때 작업당 가상 스레드를 하나 둔다. 상대 서비스의 허용량은 별도로 제한한다.
Kotlin 코루틴 중단 가능한 함수의 다음 실행 위치와 필요한 지역 값은 continuation에 보존된다. dispatcher가 재개를 예약한다. 같은 OS 스레드에서 다른 코루틴이 진행할 수도 있다. 호출 경로가 이미 suspend API이고 요청별 취소와 결과 합성을 코루틴 스코프로 관리할 때 맞는다.

두 방식 모두 312ms가 나왔다. 차이는 응답을 기다리는 300ms 동안 플랫폼 스레드에서 다른 작업을 실행할 수 있느냐다. CPU에서 실행할 OS 스레드가 바뀌면 커널이 실행 상태를 저장하고 다음 스레드의 상태를 복원한다.

가상 스레드가 지원되는 블로킹 I/O를 기다리는 동안 JVM은 캐리어 스레드를 다른 작업에 쓸 수 있다. 대기가 끝나면 가상 스레드는 사용 가능한 캐리어 스레드에서 다시 실행된다. 코루틴은 재개할 위치와 거기서 쓸 값을 저장하고 dispatcher를 통해 다음 실행을 예약한다. 그 자리에서 같은 OS 스레드가 이어받기도 한다. 다른 작업자에게 옮겨 가면 스케줄링과 캐시에 비용이 든다. 세 방식 모두 CPU 계산 자체에 필요한 시간까지 줄여 주지는 않는다. JEP 444의 가상 스레드 스케줄링, Kotlin 명세의 continuation과 상태 머신

코루틴 쪽은 runBlocking에 스레드 하나만 주고 A가 멈춰 있는 동안 B가 그 대기를 풀게 했다. 로그가 A waiting, B releases A, A resumed on same thread=true 순서로 찍혔다. 두 작업의 순서가 바뀌는 동안 OS 스레드를 바꿀 필요가 없었다. 단, 같은 자리에 동기 소켓 읽기를 그대로 넣으면 suspend fun 안이어도 그 스레드가 막힌다. 이 경우 중단 가능한 클라이언트를 쓰거나 블로킹 호출을 별도의 한정된 실행기로 넘겨야 한다. 실행한 Kotlin 예제, 코루틴 중단과 재개

진행 중인 호출과 초당 시작 건수는 어떻게 제한할까?

스레드를 더 띄울 여유가 생겨도 상대 API에는 자기 한도가 있다. 이를 지키려면 두 가지를 따로 세야 한다. 지금 진행 중인 호출 수는 시작 전에 세마포어에서 permit 하나를 얻고 본문 수신이나 오류 처리가 끝나는 finally에서 반납하면 된다.

초당 시작한 호출 수는 토큰 버킷으로 제한했다. 호출할 때 토큰을 하나 쓰고 정해진 속도로 충전하므로, 모아 둔 토큰 수만큼은 한꺼번에 시작해도 된다. 상대가 어느 1초 구간에서든 엄격한 상한을 요구하면 각 호출의 시작 시각을 기록해 그 구간 안의 건수를 세야 한다.

두 제한이 정말 다른 순간에 걸리는지 시계를 멈춰 놓고 확인했다. 동시에 진행할 호출은 하나로 제한했다. 토큰은 처음에 두 개를 주고 1초마다 하나를 보충했다. 첫 호출을 끝내기 전에 한 번 더 두드리니 자리가 없어서 거절됐다. 첫 호출을 끝내고 50ms에 다시 부르니 남은 토큰으로 시작했다. 이 호출도 끝낸 뒤 100ms에 다시 시도했더니 이번에는 자리가 비었는데도 거절됐다. 토큰이 하나 돌아온 1,000ms에야 다음 호출을 시작했다.

예제에서는 자리가 없거나 토큰이 모자라면 기다리지 않고 돌려보낸다. JVM 여러 대가 상대 API 하나의 한도를 나눠 쓴다면 인스턴스별 허용량의 합이 계약에 맞는지 보거나 시작 허가를 한곳에서 나눠 줘야 한다. 두 한도를 결합한 코드, 결정 시각과 출력

풀 크기를 정할 때도 사용자 요청 수만 보면 계산이 틀어진다. 초당 100건이 들어와 한 건마다 외부 조회 두 번이면 상대가 받는 건 초당 200건이다. 한 호출이 자리를 평균 100ms씩 차지한다면 정상 상태에서 평균 20건이 진행 중이라는 계산이 나온다(L = λW). 그런데 똑같은 평균 100ms여도 어쩌다 1초씩 붙들리는 호출이 섞이면 풀 앞에 줄이 생길 수 있다. 평균으로 첫 부하를 잡고 p95와 p99가 요청의 지연 예산을 넘는지 따로 보는 이유다. Little의 법칙과 풀의 대기 시간

예를 들어 전용 HTTP/1.1 연결이 12개이고 한 연결로 한 번에 한 요청만 보낼 수 있다면, 20건을 동시에 제출해도 연결을 쓰는 작업은 최대 12건이다. 세마포어를 12 이하로 잡으면 들어오는 수를 조절할 수 있지만 평균 20건이라는 수요까지 없어지지는 않는다. 이 상태에서 풀을 키울지 정하려면 연결을 얻기까지 기다린 시간과 연결을 빌린 뒤 반납하기까지 걸린 시간부터 나눠 봐야 한다.

부하를 올릴 때 처리량이 제자리인데 대기만 늘어나는 지점, 응답 시간의 분포, 429와 시간 초과 비율을 함께 보면 목표 지연 안에 받을 양을 정할 수 있다. HTTP/2라면 연결 개수에 더해 연결당 동시 스트림 수와 상대 서버 한도도 계산에 넣는다. HTTP/2의 동시 스트림 제한

JFR로 가상 스레드의 고정 시간 확인하기

가상 스레드가 대기 중인데도 JVM이 캐리어 스레드에서 다른 작업을 실행할 수 없는 경우가 있다. 이를 고정(pinning)이라고 한다. 고정 조건은 JDK 버전에 따라 달라서 같은 클래스 파일을 두 JDK에서 실행했다. 하나는 synchronized로 모니터를 잡은 채 150ms 동안 park한다. 다른 하나는 JNI 함수에서 Java 메서드를 다시 불러 똑같이 park한다. JFR의 jdk.VirtualThreadPinned를 켜고 실험 메서드가 스택에 있으면서 20ms 이상 이어진 이벤트만 셌다.

동일한 대기 JDK 21.0.12.1 JDK 25.0.4.1
모니터 안의 park 1건(157ms) 0건
네이티브 프레임에서 Java로 돌아와 park 1건(155ms) 1건(153ms)

모니터를 잡은 쪽은 JDK 21에서 157ms짜리 이벤트가 찍혔는데 JDK 25에서는 0건이었다. JDK 24의 JEP 491부터 모니터를 소유한 가상 스레드도 캐리어 스레드에서 분리될 수 있다. 표의 둘째 줄을 보면 JDK 25에서도 네이티브 콜백 안에서 153ms 동안 고정됐다는 이벤트가 찍혔다.

JDK 21에서 긴 I/O가 모니터를 쥔 채 멈췄다면 I/O를 락 밖으로 옮길 수 있는지 보게 된다. 그사이 다른 요청이 값을 바꿀 수 있으니 어느 시점에 상태를 다시 확인할지도 정해야 한다. 네이티브 콜백이 문제면 대기를 콜백 밖으로 옮기거나 수가 제한된 별도 작업자에게 맡길 수 있다. 실제로 고정된 호출 스택과 지속 시간, 캐리어 스레드가 얼마나 포화됐는지는 JFR로 본다. JDK 21에서 쓰던 -Djdk.tracePinnedThreads 옵션은 JDK 24부터 효과가 없다. JEP 491, JFR 실험 코드, JNI 콜백, 두 JDK의 출력

한쪽이 실패하면 먼저 시작한 요청은 어떻게 될까?

실패 실험에서는 경로를 /slow와 /fail로 바꿨다. 둘 다 필수인데 /fail이 503을 돌려주면 느린 쪽을 끝까지 기다려도 성공 응답은 만들 수 없다. 요청을 받으면 단조 시계를 기준으로 마감 시각을 한 번 정하고 세마포어를 기다릴 때, HTTP 호출을 시작할 때, 조인할 때마다 그 시각까지 남은 시간을 넘겼다. 먼저 끝난 요청에서 실패를 읽으면 finally에서 남은 Future에 cancel(true)를 요청한다. 여러 요청이 실행기를 함께 쓰므로 호출할 때마다 실행기를 닫고 취소에 응하지 않는 작업까지 기다릴 필요가 없다. HTTP 요청에는 타임아웃을 걸었고 느린 서버 작업도 600ms 뒤에 끝나게 했다. Java HTTP 클라이언트의 중단과 취소

failure outcome=IOException elapsed_ms=1 slow_effects_at_join=0
slow_effects_after_server_finished=1

느린 쪽이 요청을 받기도 전에 취소해 버리면 서버에서 무슨 일이 있었는지 볼 수 없다. 그래서 실패 쪽 핸들러는 느린 쪽이 요청을 받았다는 신호를 기다렸다가 503을 보냈다. 호출자는 1ms 만에 실패를 받았고 남은 Future 하나를 취소했다. 그때 서버 카운터는 0이었다. 조금 뒤 느린 핸들러가 끝나자 카운터는 1이 됐다.

또 한 번은 350ms를 마감으로 잡았다. 타이머와 스케줄링 오차가 있어 호출자는 355ms에 시간 초과를 받았다. 이번에도 서버에서는 뒤늦게 1이 찍혔다. 호출자 쪽에서 취소한 Future로는 서버가 이미 시작한 작업을 되돌릴 수 없었다. 실패하거나 시간이 초과됐을 때의 출력

추천 목록처럼 없어도 되는 조회라면 사정이 다르다. 빈 목록이나 ‘일시적으로 제공할 수 없음’으로 응답하기로 했다면 먼저 성공한 필수 데이터까지 버릴 이유가 없다. Kotlin coroutineScope에서는 한 자식의 일반 예외가 다른 자식의 취소로 이어진다. 스코프는 자식들이 끝날 때까지 기다린다. 예제에서 필수 작업 하나를 실패시키자 대기 중인 다른 자식 코루틴의 finally가 실행됐다. 선택 결과끼리 독립적으로 다루려면 supervisorScope 안에서 각각의 실패를 받아 처리한다.

취소에 협조해야 하는 건 여기서도 마찬가지다. 부모 요청이 취소됐는데 선택 항목 하나만 실패한 것으로 삼켜 버리지 않도록 CancellationException은 다시 던진다. 블로킹 라이브러리를 같이 쓰면 그 호출이 중단 요청에 응하는지도 따로 봐야 한다. Kotlin의 취소 전파, 형제 취소 예제

앞의 느린 핸들러가 카운터 대신 계좌 잔액을 바꿨다고 생각해 보자. 호출자는 시간 초과를 받았는데 서버에서는 이미 송금이 끝났을 수 있다. 이때 같은 승인을 곧바로 다시 보낼 수는 없다. 그때 먼저 필요한 값은 서버에 남은 거래 식별자와 처리 상태다. 송금 결과를 받지 못했을 때의 재시도
