조회 A는 응답에 150ms, B는 300ms가 걸린다. 두 값이 모두 필요하고 B의 요청을 만들 때 A의 값은 쓰지 않는다. A가 끝나기를 기다렸다가 B를 보내면 기다리는 시간만 450ms다. 둘을 함께 시작하면 둘 중 늦은 응답이 돌아오는 300ms에 결과를 합칠 수 있다. 반대로 A에서 받은 토큰으로 B를 호출해야 한다면 겹칠 수 있는 대기 구간도 없다.

순차로 473ms, 함께 보내면 312ms

루프백 HTTP 서버의 두 핸들러가 각각 150ms와 300ms를 기다린 뒤 경로 이름을 반환하게 했다. 클라이언트는 같은 HttpClient로 두 응답을 모두 읽고 값이 맞아야 다음 시도를 시작했다. Apple M4 Pro, macOS ARM64, JDK 25에서 모드마다 다섯 번씩 잰 중앙값은 순차 473ms, 플랫폼 스레드 두 개를 둔 풀 312ms, 작업당 가상 스레드 하나 312ms였다. 겹친 것은 외부 응답을 기다리는 구간이다. 두 건만으로 높은 부하에서의 처리량 우열까지 정할 수는 없다. HTTP 서버와 클라이언트 소스 · 시도별 값과 실행 명령

여기서 포크(fork)는 독립적인 조회를 시작하는 일이고 조인(join)은 같은 요청에 속한 결과를 합치는 일이다. 이 형태는 여러 실행기로 구현할 수 있다. 실험은 ExecutorCompletionService로 끝난 순서에 응답을 받고 경로 이름을 키로 넣어 어느 응답이 먼저 오든 같은 결과를 만든다.

어디에 실행 상태를 보관할까?

실행 방식 대기 중에 일어나는 일 선택할 상황
플랫폼 스레드 풀 HotSpot의 플랫폼 스레드는 보통 OS 스레드 하나에 대응한다. 동기 소켓 읽기에 걸린 작업자는 그동안 같은 풀의 다른 일을 맡을 수 없다. 동시에 진행할 작업이 적거나 CPU 연산이 중심일 때 작업자 수와 큐를 제한한다.
가상 스레드 JVM은 여러 가상 스레드를 운반 스레드(carrier)에서 실행한다. 지원되는 블로킹 I/O에서 실행을 중단하면 Java 호출 스택을 보존한 채 carrier를 다른 작업에 쓸 수 있다. 동기 Java API를 쓰면서 많은 연결이 응답을 기다릴 때 작업당 가상 스레드를 하나 둔다. 상대 서비스의 허용량은 별도로 제한한다.
Kotlin 코루틴 중단 가능한 함수의 다음 실행 위치와 필요한 지역 값은 continuation에 보존된다. dispatcher가 재개를 예약한다. 같은 OS 스레드에서 다른 코루틴이 진행할 수도 있다. 호출 경로가 이미 suspend API이고 요청별 취소와 결과 합성을 코루틴 스코프로 관리할 때 맞는다.

운영체제가 플랫폼 스레드를 전환하면 커널 스케줄러가 실행 문맥을 넘긴다. 코루틴의 중단 한 번에는 소스 수준 실행 상태 저장과 재개 예약 비용이 든다. 같은 OS 스레드에서도 중단과 재개가 일어난다. 다른 작업자에서 재개하면 스케줄링과 캐시 비용이 생길 수 있다. 가상 스레드도 마운트·언마운트가 필요하다. 계산에 CPU가 부족하면 셋 모두 같은 CPU 시간을 두고 경쟁한다. JEP 444의 가상 스레드 스케줄링 · Kotlin 명세의 continuation과 상태 머신

한 스레드의 runBlocking에서 A를 중단시키고 B가 A의 대기를 풀게 했다. 출력은 A 대기, B 실행, A 재개 순서였고 A가 재개한 스레드는 처음과 같았다. 실행 흐름을 바꾸는 데 OS 스레드 두 개가 필요한 것은 아니다. suspend fun 안에서 동기 소켓을 그대로 읽으면 그 작업은 여전히 스레드를 막는다. 중단 가능한 클라이언트를 쓰거나 블로킹 호출을 한도가 있는 실행 환경에 격리한다. 실행한 Kotlin 예제 · 코루틴 중단과 재개

진행 중인 호출과 초당 시작 건수는 어떻게 제한할까?

동시성 한도는 호출 전에 세마포어의 허가를 얻고 본문 수신이나 오류 처리가 끝나면 finally에서 돌려주는 방식으로 지킨다. 초당 요청 한도는 호출 시작 시 토큰을 하나 차감하고 일정한 속도로 충전하는 버킷으로 지킬 수 있다. 버킷의 용량이 허용하는 순간 버스트도 계약에 포함된다. 엄격한 이동 구간 제한이라면 해당 구간의 시작 시각을 기록하는 방식에 맞춘다.

가상 시계를 쓰는 실험에서는 동시 자리가 하나, 초기 토큰이 두 개이고 초마다 한 개를 충전한다. 첫 호출이 진행 중일 때 두 번째 시도는 동시성으로 거절된다. 첫 호출을 끝내고 50ms에 시작한 호출은 성공한다. 이 호출까지 끝난 100ms에는 자리가 비어 있어도 요청률 때문에 거절된다. 1,000ms에 토큰 하나가 돌아와 다시 시작한다. 예제는 진입 실패 시 즉시 반환한다. 여러 JVM이 한 계약을 공유하면 인스턴스별 허용량 합이나 공통 제한기도 확인해야 한다. 두 한도를 결합한 코드 · 결정 시각과 출력

한도를 잡을 때는 대상 API가 실제로 받는 호출부터 센다. 예를 들어 초당 사용자 요청 100건이 각자 외부 API를 두 번 부르면 초당 외부 호출은 200건이다. 외부 호출 평균 점유 시간이 100ms라면 정상 상태의 평균 진행 건수는 약 20이다(L = λW). 평균은 같아도 일부 요청이 1초씩 자리를 차지하면 풀 앞에서 기다리는 시간이 달라진다. 평균은 초기 부하 가정에 쓰고 p95·p99는 지연 예산과 비교한다. Little의 법칙과 풀의 대기 시간

HTTP/1.1에서 전용 연결 12개가 한 번에 한 요청씩 처리한다면 동시에 20건을 제출해도 연결을 잡는 것은 최대 12건이다. 연결이 필요한 작업의 세마포어를 가용 연결 이하에서 시작해도 이미 꽉 찬 평균 수요를 해결할 수는 없다. 풀 획득 대기, 연결을 잡고 있는 시간, 응답 지연 분포, 429와 시간 초과율을 따로 기록한다. 부하를 단계별로 올려 처리량이 멈추는데 대기만 늘어나는 지점을 찾고 목표 지연 안에서 감당할 수 있는 요청만 받아들인다. HTTP/2에서는 연결당 동시 스트림과 상대 서버의 한도도 함께 센다. HTTP/2의 동시 스트림 제한

가상 스레드가 운반 스레드를 붙잡고 있는지 확인하기

같은 Java 클래스 파일에 두 가지 대기 경로를 담았다. 하나는 모니터(synchronized) 안에서 150ms를 park한다. 다른 하나는 JNI 함수가 Java 메서드를 다시 불러 같은 대기를 한다. JFR에서 jdk.VirtualThreadPinned를 켜고 20ms 이상이면서 실험 메서드가 스택에 있는 이벤트를 셌다.

동일한 대기 JDK 21.0.12.1 JDK 25.0.4.1
모니터 안의 park 1건 · 157ms 0건
네이티브 프레임에서 Java로 돌아와 park 1건 · 155ms 1건 · 153ms

JDK 24에 반영된 JEP 491은 모니터를 소유한 가상 스레드도 carrier에서 분리될 수 있게 했다. JDK 21에서 재현된 긴 모니터 내부 I/O라면 락 구간 밖으로 I/O를 옮기는 방법을 검토한다. 락이 보호하던 상태를 다시 확인할 경계도 정해야 한다. JDK 25에서 남은 네이티브 콜백처럼 긴 대기는 경계를 바꾸거나 상한이 있는 별도 작업자에서 처리할 수 있다. JFR에서 실제 고정 지속 시간·호출 스택과 carrier 포화를 함께 확인한다. -Djdk.tracePinnedThreads는 JDK 21의 진단 옵션이며 JDK 24부터 효과가 없다. 한쪽이 실패하면 먼저 시작한 요청은 어떻게 될까?

두 조회가 모두 필수라면 한쪽의 503으로 이미 정상 응답을 만들 수 없다. 실험에서는 요청 입구에서 단조 시계로 마감 시각을 정하고 세마포어 대기·각 HTTP 요청·결과 조인에 남은 시간만 전달한다. 끝난 작업부터 실패를 확인하고 finally에서 남은 Future에 cancel(true)를 요청한다. 실행기는 여러 요청이 공유한다. 매 요청에서 취소에 응하지 않는 작업의 종료를 무한정 기다리지 않는다. 이 실험의 HTTP와 서버 작업에는 각각 시간 경계가 있다. Java HTTP 클라이언트의 중단과 취소

failure outcome=IOException elapsed_ms=1 slow_effects_at_join=0
slow_effects_after_server_finished=1

503을 내는 핸들러가 느린 쪽의 요청 수신을 확인한 뒤 응답하게 했다. 호출자는 1ms 뒤 실패를 받았고 남은 Future 하나를 취소했다. 이때 서버의 효과 카운터는 0이었다. 느린 서버 핸들러는 계속 실행돼 카운터가 1이 됐다. 350ms의 마감을 둔 실행도 355ms 뒤 시간 초과로 돌아왔지만 서버 카운터는 나중에 1이 됐다. 타이머와 스케줄링 오차가 있다. 호출자의 취소가 다른 프로세스에서 이미 시작한 작업을 되돌리지도 않는다. 실험의 실패·시간 초과 출력

선택 정보인 추천 목록이라면 전체 요청의 계약에 빈 목록이나 ‘일시적으로 제공할 수 없음’을 두고 성공한 필수 데이터와 함께 응답할 수도 있다. Kotlin의 coroutineScope는 한 자식의 일반 예외를 다른 자식의 취소로 전파하고 자식들의 종료를 기다린다. 선택 결과를 독립적으로 처리할 때는 supervisorScope 안에서 해당 실패를 명시적으로 수집한다. 취소는 협력적이다. 부모가 취소된 경우에는 CancellationException을 다시 던진다. 블로킹 라이브러리가 중단 요청을 따르는지도 확인한다. 예제에서는 필수 자식 하나가 실패하자 대기하던 형제의 finally가 실행됐다. Kotlin의 취소 전파 · 형제 취소 예제

서로 독립인 조회를 합치는 규칙과 이미 처리됐을 수도 있는 송금 승인을 다시 호출하는 규칙은 다르다. 승인의 결과를 받지 못했다면 서버가 남긴 거래 식별자와 상태부터 확인해야 한다. 다음 편에서 송금 확정과 재시도 조건을 다룬다.
