**TL;DR**

10주차에 CI에 게이트를 붙였다.
전부 초록이었다.
그 상태로 다시 훑었더니 막으려던 것이 통과하는 자리가 여섯 군데 있었다.
초록불이 증명하는 것은 "검사가 돌았다"까지다.
"검사가 옳다"는 별도로 증명해야 한다.

## 초록불은 검사가 돌았다는 뜻이다

과제는 검증을 기계에 새기는 것이었다.
파이프라인 시간을 잰다.
비싼 검증에 실행 조건을 건다.
번들 예산을 건다.
AI 리뷰에서 반복되는 지적은 룰로 내린다.
다 했고 CI는 초록이었다.

문제는 그다음이었다.
게이트를 걸었다는 사실과 게이트가 막는다는 사실은 다르다.
후자를 확인하려면 막혀야 할 입력을 실제로 넣어 봐야 한다.
그걸 안 한 자리마다 구멍이 있었다.

## 허용 목록으로 만든 필터는 모르는 경로에서 열린다

E2E는 12개에 20초다.
문서만 고친 PR에서 돌릴 이유가 없다.
그래서 경로 필터를 걸었다.
`src`, `e2e`, `scripts`, workflow, config가 바뀌면 실행하고 나머지는 생략한다.

루트에 파일을 몇 개 만들어 찍어 봤다.

```
instrumentation.ts   -> 생략
middleware.ts        -> 생략
proxy.ts             -> 생략
src/foo.config.ts    -> 실행
docs/a.md            -> 생략
```

앞의 셋은 Next 런타임이 읽는 파일이다.
루트에 런타임 파일을 새로 만들면 가장 비싼 게이트가 조용히 빠진다.

허용 목록은 모르는 경로에서 생략한다.
거부 목록은 모르는 경로에서 실행한다.
같은 목적의 필터인데 기본값 하나가 안전과 위험을 가른다.

바꾼 판정은 이렇다.
바뀐 경로가 전부 무해 목록에 들어갈 때만 생략한다.
하나라도 모르는 경로가 있으면 실행한다.
변경 목록을 읽지 못했을 때도 실행한다.
그 자리에서 생략하면 조용한 false green이 된다.

원인은 위치였다.
판정이 workflow YAML 안의 bash 30줄이었다.
실행해 볼 수단이 없으니 케이스를 쓸 수도 없었다.
스크립트로 옮기고 12개 케이스를 쓰자 그 자리에서 드러났다.

가장 미묘한 로직이 가장 검사가 없는 자리에 있었다.

## 게이트가 자기 표의 키만 순회하면 새 이름은 통과한다

번들 예산은 라우트별 바이트 수를 임계값과 비교한다.
홈 618 KiB, 상품 목록 635 KiB.
7주차 측정값에 5%를 더한 값이다.

진단 파일에 `/checkout`을 넣고 5,000,000 B를 줬다.
종료 코드 0이었다.

비교 코드가 예산표의 키만 돌고 있었다.
표에 없는 라우트는 표에 나타나지도 않는다.
라우트를 새로 만드는 것만으로 예산을 빠져나간다.

지금은 둘 중 한 곳에 이름이 있어야 통과한다.
예산을 정한다.
예산을 두지 않을 거면 이유를 적고 제외 목록에 넣는다.
실습용 화면과 Next 내부 라우트가 제외 목록에 있다.

예산에는 층이 하나 더 붙었다.
예산은 상한만 본다.
618 KiB 아래에서 588에서 610으로 오르는 22 KiB는 통과한다.
그래서 측정값 자체를 커밋된 기준선 파일과 맞춘다.
번들이 바뀌면 같은 PR에 기준선 diff가 올라온다.
리뷰가 "무엇이 몇 바이트 늘렸나"를 숫자로 본다.

## 기본값은 게이트를 앞에서 무력화한다

환경 변수 검증은 build 전에 돈다.
`APP_ORIGIN`이 없거나 호스트까지 포함한 URL이 아니면 build를 막는다.

값을 읽는 모듈에는 이런 주석이 있었다.

```ts
// 기본값은 두지 않는다. 조용한 localhost 기본값이 불일치를 숨기고 결과물에 굳는다.
```

그런데 `Dockerfile`이 그 기본값을 채우고 있었다.

```dockerfile
ARG APP_ORIGIN=http://127.0.0.1:3000
```

`--build-arg` 없이 빌드해도 검증이 통과한다.
runner 단계에는 값이 아예 없어서 요청마다 터진다.
게이트가 막으려던 설정 사고가 게이트 안쪽에 있었다.

기본값을 지우자 인자 없는 빌드가 builder 단계 0.4초에 멈춘다.
인자를 준 빌드는 이미지 환경에 값이 남는다.
컨테이너 URL에서 smoke 3개가 1.4초에 통과한다.

## 중앙값으로 병목을 고르면 순위가 틀린다

파이프라인 시간을 재려고 `pnpm check` 한 줄을 스텝 12개로 나눴다.
스텝별 중앙값은 이렇게 나왔다.

| 스텝 | 중앙값 |
| --- | ---: |
| 단위·DOM 테스트 | 20s |
| Playwright 시스템 의존성 설치 | 14s |
| E2E | 14s |
| 브라우저 다운로드 | 11s |
| build | 10s |

1위는 테스트, 2위가 의존성 설치다.
그래서 브라우저 다운로드를 줄이는 실험을 했다.
중앙값은 11초에서 6초로 줄었는데 job 전체는 그대로였다.
채택 기준을 미리 정해 뒀던 덕에 기각으로 끝났다.

마지막 제출 실행에서 `runtime` job이 429초였다.
그중 347초가 의존성 설치 한 스텝이었다.
같은 명령이 다른 러너에서는 13초에서 28초 사이였다.

중앙값 14초로 3위였던 스텝의 최악값이 나머지를 다 합친 것보다 크다.
순위를 중앙값으로만 매기면 변동이 큰 스텝은 계속 아래에 있다.
최악값과 폭을 같이 봐야 순위가 맞는다.

## 관측에도 값이 있다

스텝을 나눈 김에 한 줄 구성과 나란히 쟀다.

| 구성 | warm 중앙값 | 범위 |
| --- | ---: | ---: |
| `pnpm check` 한 줄 | 103s | 101~112 |
| 스텝 12개 | 119s | 106~130 |
| job 2개로 분리한 임계경로 | 90s | 75~118 |

스텝을 나눈 구성이 한 줄 구성보다 16초 느리다.
스텝마다 `pnpm`이 새로 뜨는 비용이다.
어느 검증이 느린지 아는 대가가 13%였다.

그래도 나눈 구성을 유지한다.
어느 스텝이 느린지 모르는 상태로 돌아가면 다음 측정의 출발점이 없다.

job을 둘로 나눈 것은 채택했다.
브라우저도 build 산출물도 필요 없는 검증이 build와 E2E 뒤에 줄을 서 있었다.
분리한 job은 Playwright 설치 27초를 치르지 않는다.
사람이 기다리는 시간은 119초에서 90초로 줄었다.
총 러너 시간은 119초에서 137초로 늘었다.
기다리는 시간을 compute와 바꾼 것이다.

여기서 한 번 틀렸다.
처음에 표본 3개를 보고 "두 측정 범위가 겹치지 않는다"고 적었다.
같은 구성을 다시 재니 75~118로 넓어져 위쪽에서 겹쳤다.
공유 러너의 변동이 줄인 폭과 같은 자리수다.
중앙값 차이는 남았지만 문장은 정정했다.
표본 수를 적지 않은 비교는 다음 사람이 그대로 인용한다.

## 게이트 자신이 회귀한다

승격한 룰 하나가 있었다.
화면에서 계측 함수를 직접 import하지 않는다.
ESLint 패턴으로 alias, 상대경로, 확장자 표기, 동적 import를 막는다.

자가 검증 결과를 문서에 표로 적어 뒀다.
그게 문제였다.
패턴 문자열 하나가 빠져도 `pnpm lint`는 통과한다.
룰이 조용히 약해지면 본 게이트는 초록으로 남는다.

지금은 룰의 테스트가 룰보다 먼저 돈다.
확인차 룰을 세 가지로 훼손해 봤다.

| 훼손 | 결과 |
| --- | --- |
| 확장자 패턴 제거 | 해당 케이스만 실패 |
| 동적 import 룰 제거 | 해당 케이스만 실패 |
| 테스트 파일 예외에서 제한 제거 | 해당 케이스만 실패 |

복원하면 11개가 다시 통과한다.

이 배치는 원래 있던 것이다.
`env:test`가 `env:check`를, `size:test`가 `size:check`를 앞에서 지킨다.
나머지 게이트에 같은 짝을 붙이지 않았을 뿐이다.

## 문서는 규칙을 강제하지 못한다

팀 규칙 문서에 "커밋에 AI 서명을 넣지 않는다"가 있었다.
작업 중에 서명이 붙은 커밋 5개를 만들었다.
사람이 눈으로 찾아서 지웠다.

규칙이 문자열로 판별 가능하면 문서에 두는 것은 선택이 아니다.
지금은 `commit-msg` 훅과 CI가 같은 스크립트로 판정한다.
서명이 붙어 있던 원본 커밋 5개를 그 스크립트에 넣어 거부를 확인했다.

같은 자리가 하나 더 있었다.
주석의 문체 규칙이다.
의인화를 쓰지 않고 영어식 직역을 쓰지 않는다는 규칙도 문서에만 있었다.
게이트를 만들어 돌리자 첫 실행에서 직역 표현이 잡혔다.

문체 전부를 기계가 가릴 수는 없다.
그래서 반복해서 지적된 표현만 목록으로 고정했다.
목록에 없는 표현은 사람 리뷰가 본다.

## 한계와 남은 것

지금 구성에는 눈이 먼 자리가 있다.

CI 구성 검사는 YAML 파서를 쓰지 않는다.
의존성을 늘리지 않으려고 필요한 키만 줄 단위로 읽는다.
들여쓰기를 크게 바꾸면 검사가 통과한다.
검사 대상이 workflow 두 개뿐이라 받아들인 교환이다.
늘어나면 파서를 넣는다.

목록 기반 게이트는 목록 밖을 통과시킨다.
문체 검사도, 커밋 서명 검사도 그렇다.
그건 누락이 아니라 경계다.
경계를 코드 주석과 문서에 적어 두지 않으면 다음 사람이 누락으로 읽는다.

`merge_group`은 저장소 설정에 달려 있다.
PR에서 생략한 검증을 병합 직전에 다시 도는 방어선인데, merge queue를 켜지 않으면 이 트리거는 발생하지 않는다.
코드에 있다는 것과 도는 것은 다르다.

룰을 만들며 오탐 셋과 미탐 하나를 냈다.
`복원한다`가 `원한다` 패턴에 걸렸다.
주석에 쓴 트리거 이름은 트리거 사용으로 잡혔다.
`좁힐 필요가 있다`는 패턴이 좁아서 빠졌다.
룰을 좁히는 근거는 오탐이고 넓히는 근거는 미탐이다.
넷 다 케이스로 남겼다.

게이트로 막을 수 없는 실수도 있다.
측정 없이 기각한 것, 표본 3개로 단정한 것, 예산선을 낮춰 빨간불을 만든 것.
이건 문자열로 판별되지 않는다.
측정 전에 채택 기준을 고정한다.
표본 수를 같이 적는다.
증거가 무엇까지 증명하는지 스스로 묻는다.
이 절차로만 줄어든다.

## 남은 한 줄

1주차에 세운 기준은 "설명할 수 없는 코드는 커밋하지 않는다"였다.

10주차에 형태가 하나 붙었다.

이 실수가 다시 들어오면 무엇이 막는가.

답이 "리뷰에서 보겠다"이면 그 실수는 다시 들어온다.
