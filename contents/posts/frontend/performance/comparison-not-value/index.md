**TL;DR**

홈 FCP가 899ms 나빠진 원인을 찾는 동안 비교를 세 번 잘못 세웠다.

값이 부정확해서가 아니다. 세 번 다 무엇과 무엇을 나란히 놓아야 하는지를 정하지 않았다. 기준이 없었고, 기준이 어긋났고, 마지막에는 기준이 모자랐다.

새로 잰 건 한 번뿐이다. 나머지 둘은 이미 커밋한 파일을 다시 읽어서 잡혔다.

## 추정치를 지연으로 읽었다

Lighthouse가 홈 FCP를 1,360ms에서 2,259ms로 보고했다. 899ms 느려진 것으로 읽고 원인을 찾기 시작했다.

기본 감속은 관측이 아니라 추정이다. 비감속으로 한 번 관측한 요청 집합을 감속된 가상 링크에 얹어 재생한다. 같은 두 빌드에 감속을 실제로 걸고 재면 1,627ms와 1,705ms다. 차이는 78ms다.

물었어야 할 것은 왜 899ms 느려졌느냐가 아니라 이 899ms가 무엇과 무엇의 차이냐였다. 원인 사냥은 그 질문을 건너뛰고 시작됐다.

## 총합으로 부분 창을 반박했다

첫 원인으로 폰트를 적었다. 셸이 서버 컴포넌트로 올라가면서 한글 문구가 첫 flush에 실렸고, navigation 이후 300ms 안에 시작된 Pretendard 서브셋 요청이 2건 64,312B에서 7건 183,324B로 늘었다.

이 주장을 나중에 폐기했다. 근거는 폰트 요청 총합이었다. 세 조건 모두 10건 265,088B로 같았다. 늘어난 게 없으니 원인일 수 없다고 봤다.

총합은 실제로 같다. 그런데 원래 주장은 총합에 대한 것이 아니었다. 첫 페인트보다 한참 앞인 그 300ms 구간에 무엇이 들어왔는지에 대한 것이었다. 두 값은 재는 대상이 다르다. 총합이 같다는 사실은 배분이 같다는 뜻이 아니다.

같은 raw를 요청 시각으로 다시 나누면 갈린다.

```js
const items = report.audits['network-requests'].details.items
const fonts = items.filter((item) => item.resourceType === 'Font')
const firstBurst = fonts.filter((item) => item.networkRequestTime < 300)

// fonts는 세 조건 모두 10건 265,088B.
// firstBurst는 2건 64,312B / 7건 183,324B / 2건 64,312B로 갈린다.
```

각 조건 5회 회차 전부 편차가 없었다. 총합은 이 주장을 반증하지 못한다. 폐기할 근거가 사라졌다. 주장이 참이라는 뜻은 아니다.

폐기 근거가 무너진 것을 알게 된 건 한참 뒤다. 그사이에 폐기한 자리를 다른 설명으로 채웠다.

## 두 값이 같이 움직이는데 하나를 골랐다

document 응답이 5ms에 끝나던 것이 509ms까지 열려 있게 됐다. 899ms는 Lantern이 그 열린 document를 CSS의 선행 의존 비용으로 계산한 값이라고 적었다.

Before와 After만 놓고 보면 그럴듯하다. 문제는 그 둘 사이에서 document와 폰트 버스트가 함께 움직였다는 것이다. 함께 움직이는 두 값에서는 어느 쪽이 원인인지 정해지지 않는다. 폰트를 통째로 차단한 회차도 있었지만 그것으로도 못 가른다. 차단은 대역폭과 글꼴 이용 가능성을 함께 바꿔서 역시 조건이 하나만 다르지 않다.

가를 조건은 이미 있었다. 셸 문구만 라틴 문자로 바꾼 회차다. 셋 다 같은 시뮬레이션 감속이고 각 5회 중앙값이다.

| 값 | Before | After 한글 | 라틴 치환 |
| --- | ---: | ---: | ---: |
| document 완료 | 5ms | 509ms | 509ms |
| 300ms 이전 폰트 | 64,312B | 183,324B | 64,312B |
| CSS 자체 `wastedMs` | 303ms | 302ms | 302ms |
| render blocking 전체 추정 | 732ms | 1,625ms | 725ms |
| Lantern FCP | 1,360ms | 2,259ms | 1,356ms |

라틴 치환은 document가 After와 똑같이 509ms까지 열려 있다. 그런데 render blocking 추정은 725ms로 Before 수준이다. document를 원인으로 두면 이 열을 설명할 수 없다.

혼자 움직인 값은 300ms 이전 폰트 바이트 하나다. CSS 자체 비용은 302ms에서 303ms로 세 조건이 같은데 render blocking 전체 추정만 두 배가 된다. 폐기했던 첫 주장이 가리킨 값이 그것이다.

## 새로 잰 건 한 번뿐이었다

세 오류의 형태가 다르다. 처음에는 비교 기준이 없었다. 그 숫자가 무엇과 무엇의 차이인지 정하지 않은 채 원인을 찾았다. 두 번째는 기준이 어긋났다. 부분 창에 대한 주장을 총합으로 반박했다. 세 번째는 기준이 모자랐다. 두 후보가 함께 움직이는 조건 둘만 놓고 하나를 골랐다.

새 데이터가 필요했던 건 첫 번째뿐이다. 적용형 감속으로 다시 재야 했다. 나머지 둘은 이미 커밋한 raw를 다시 읽어서 잡혔다. 라틴 치환 회차는 두 번째 오류를 적을 때부터 갖고 있었다. document가 After와 같다는 것을 확인하지 않고 document를 골랐을 뿐이다.

대조군을 새로 만들어야 했던 게 아니다. 손에 쥔 것을 쓰지 않았다.

## 아직 모르는 것

적용형 78ms도 Lab 측정이다. 실제 사용자가 겪는 지연이라고 말할 수 없다. 확인된 것은 같은 두 빌드가 감속 방식에 따라 다른 결과를 냈다는 것까지다.

판별 변수를 찾은 것과 기전을 설명한 것도 다르다. 300ms 이전 폰트 바이트가 혼자 움직였다는 데까지는 세 조건 대조로 확인했다. 그 바이트가 Lantern 안에서 어느 경로를 거쳐 FCP 추정에 반영되는지는 특정하지 않았다. 여기서 또 그럴듯한 설명을 적으면 네 번째가 된다.
