상품 목록의 히스토리 옵션에서 `{ history: 'push' }`를 빈 객체로 바꿨다. nuqs 2.9.0은 옵션이 없으면 `replace`를 쓴다. 카테고리를 바꾼 뒤 뒤로가기를 눌러도 이전 목록으로 돌아가지 못하는 변경이다.

단위 테스트와 통합 테스트 304개는 전부 통과했다. production build를 띄운 E2E 두 건만 실패했다. Stryker 변이 점수 99.37%에서 끝까지 살아남은 하나였다.

99.37%면 충분하다고 쓰기에는 마지막 하나가 너무 정확한 곳에 남아 있었다. 그렇다고 100%를 만들자고 E2E를 변이마다 돌리는 것도 이상했다. 이 숫자를 어떻게 해석해야 할지 한동안 결론을 못 냈다.

출발점은 테스트 개수가 아니었다. 어떤 실패를 어느 실행 환경에서 잡을 것인가. 15개 검증 대상을 먼저 적고 각 테스트가 빨간불이 될 이유를 정했다. 구현 뒤에는 코드를 열 군데 망가뜨렸고, 단위 규칙 7개 파일에는 변이 158개를 전수로 걸었다.

## 빨간불이 알려줄 내용을 먼저 적었다

시작할 때 이미 테스트가 269개 있었다. 숫자를 늘리는 일만으로는 빈 곳을 알기 어려웠다. 기존 테스트가 무엇을 보장하는지도 한 문장으로 설명하기 힘들었다.

검증 대상마다 실패했을 때 알게 될 사실을 먼저 적었다.

| 검증 대상 | 방법 | 빨간불이 알려주는 것 |
| --- | --- | --- |
| 담기 토글과 개수 파생 | 단위 | 같은 상품을 다시 눌러도 빠지지 않거나 ID 수와 헤더 개수가 어긋난다 |
| 카테고리 변경 | 통합 | URL은 바뀌지만 요청과 목록이 이전 조건에 남거나 page가 1로 돌아가지 않는다 |
| 뒤로가기와 앞으로가기 | E2E | URL만 돌아가고 목록은 남거나 히스토리 한 칸이 두 칸으로 쌓인다 |

담기 규칙은 React 밖에서도 성립한다. `toggleCartId`와 `cartCountOf`를 순수 함수로 꺼내자 DOM 없이 경계를 전부 밟을 수 있었다. hook이 그 규칙을 실제로 구독하는지는 상품 카드와 헤더를 함께 그리는 통합 테스트가 맡았다.

```ts
export const toggleCartId = (ids: readonly string[], productId: string) =>
  ids.includes(productId)
    ? ids.filter((existing) => existing !== productId)
    : [...ids, productId]

export const cartCountOf = (ids: readonly string[]) => ids.length
```

처음에는 “빈 목록에서 빼려 해도 빈 목록 그대로다”라는 기대를 썼다. 토글은 빈 목록에서 상품을 추가해야 한다. 순수 함수 테스트가 바로 실패했고 기대를 “상품 하나만 남는다”로 고쳤다. 화면을 그렸다면 규칙을 잘못 이해한 것인지 배선이 끊긴 것인지부터 갈라야 했을 문제였다.

이 실패는 꽤 민망했지만 테스트의 역할을 가장 빨리 보여줬다. 구현이 아니라 내가 적은 기대가 틀렸다. 규칙을 작은 함수로 꺼내지 않았다면 실패 원인을 React 배선부터 의심했을 가능성이 컸다.

반면 뒤로가기는 브라우저가 소유한 동작이다. jsdom의 history는 호출을 흉내 내지만 사용자가 실제로 누르는 뒤로가기와 Next.js 라우팅이 이어지는 구간을 대신하지 못한다. 이 항목만 production build 위의 Playwright로 올렸다.

## fetch를 바꿔치기하자 요청이 검증에서 사라졌다

7개 테스트 파일이 `vi.stubGlobal('fetch', ...)`를 쓰고 있었다. 응답을 원하는 순서로 만들기는 쉬웠지만 앱의 요청은 네트워크까지 가지 않았다. URL 조립이 맞아도 전송 경로가 다른 주소를 호출하면 테스트는 통과한다. `AbortSignal`을 fetch에 넘겼는지만 검사할 뿐 진행 중인 요청이 실제로 끊기는지도 알 수 없었다.

fetch는 그대로 두고 MSW가 요청을 가로채게 바꿨다.

```ts
const server = setupServer(...handlers)

beforeAll(() => {
  server.listen({ onUnhandledRequest: 'error' })
})

afterEach(() => {
  server.resetHandlers()
})
```

기본 핸들러에는 성공 응답만 뒀다. 오류, 빈 결과, 지연은 해당 테스트가 `server.use`로 덮는다. 등록하지 않은 요청은 실패시켰다. 개발 서버가 우연히 떠 있는지에 따라 테스트 결과가 달라지는 일을 막기 위해서다.

목록을 만드는 코드도 두 벌로 두지 않았다. route와 MSW 핸들러가 `selectProducts`를 함께 호출한다. 검증과 mock 지연, `scenario=empty|error` 판정은 요청을 받은 route에 남겼다. 조건에서 상품을 고르고 정렬하고 페이지를 자르는 규칙만 공유했다.

이관 뒤 취소 테스트의 질문도 달라졌다.

```ts
server.use(
  http.get(TRANSPORT_URL, async () => {
    await delay('infinite')
    return HttpResponse.json({})
  }),
)

const pending = fetchJson(TRANSPORT_URL, controller.signal)
controller.abort()

await expect(pending).rejects.toMatchObject({ name: 'AbortError' })
```

이제 “신호 객체의 aborted가 true인가”가 아니라 “진행 중인 요청이 AbortError로 끝나는가”를 본다. 네트워크 실패도 `Promise.reject(new TypeError())`를 직접 돌려주지 않는다. `HttpResponse.error()`가 만든 실제 fetch 실패를 전송 계층이 `NetworkError`로 바꾸는 경로를 지난다.

## 모든 테스트를 jsdom에 두자 취소 결과가 달라졌다

테스트 37개 파일이 모두 jsdom에서 돌고 있었다. 그중 22개는 DOM을 전혀 쓰지 않았다. `.test.ts`는 node, `.test.tsx`는 jsdom에서 실행하도록 Vitest project를 둘로 나눴다.

| 구성 | 환경 셋업 | 벽시계 | 결과 |
| --- | ---: | ---: | --- |
| 전부 jsdom 37파일 | 약 23초 | 4.6초 | 36파일 통과, 1파일 실패 |
| node 22파일, jsdom 15파일 | 약 12초 | 3.3초 | 37파일 통과 |

환경 셋업은 절반이 됐지만 벽시계 차이는 1.3초였다. 워커가 병렬로 준비되므로 셋업 감소량이 실행 시간에 그대로 더해지지 않았다. 속도만 보면 큰 변화라고 쓰기 어렵다.

분리를 유지한 이유는 마지막 열이다. 전부 jsdom으로 돌리면 `http.test.ts`의 취소 테스트가 실패했다. jsdom의 fetch 구현과 node fetch가 취소를 다르게 처리했다. 서버에서도 실행되는 전송 계층을 브라우저 흉내 하나에서만 확인하면 테스트 결과가 실행 의미와 달라졌다.

확장자 규약에는 구멍이 있다. JSX를 쓰지 않는 DOM 테스트는 `.tsx`라는 이름만 보고 이유를 알아채기 어렵다. 현재 코드에서는 DOM 테스트가 React를 그리고 대부분 JSX를 썼다. 예외는 `renderHook` 테스트 하나뿐이었다. 파일별 주석을 늘리는 대신 ESLint가 `.test.ts`의 `@testing-library/*` import를 error로 막게 했다. 규약이 어긋나면 CI보다 먼저 파일 확장자를 바꾸라는 메시지가 나온다.

환경을 나누며 숨은 12초도 발견했다. node에서 route 테스트 하나가 12.4초였고 jsdom에서는 45ms였다. mock API의 500ms 지연을 끄는 조건이 `NODE_ENV === 'test'`였는데 jsdom에서는 Vite가 값을 치환했고 node에서는 셸의 `development`가 남았다. Vitest 설정에 테스트 환경을 명시하자 두 project가 같은 조건으로 실행됐다.

## E2E를 check에 넣되 build는 한 번만 했다

E2E를 `pnpm test`에는 넣지 않았다. 저장할 때마다 도는 짧은 루프에서 production build는 너무 비쌌다. 커밋과 PR의 게이트인 `pnpm check`에는 넣었다. 별도 명령만 만들고 게이트 밖에 두면 실행되지 않는 테스트가 되기 쉬웠다.

처음에는 `check`의 build가 끝난 뒤 Playwright webServer가 다시 build했다. E2E 구간만 8.8초가 걸렸다. 실행 경로를 둘로 나눴다.

```json
{
  "test:e2e": "pnpm build && playwright test",
  "test:e2e:prebuilt": "playwright test",
  "check": "... && pnpm build && ... && pnpm test:e2e:prebuilt"
}
```

단독 실행은 산출물을 직접 만들고 `check`는 앞 단계의 산출물을 재사용한다. E2E 구간은 2.5초가 됐다. `prebuilt`만 실행하면 산출물이 없을 때 실패한다. 개발 서버로 조용히 내려가는 경로는 두지 않았다. 서버 컴포넌트의 사전 렌더와 번들 분할은 production build에서만 확인되기 때문이다.

## 열 군데 중 두 군데가 살아남았다

테스트 코드는 그대로 두고 구현을 한 곳씩 망가뜨렸다. 이미 겨냥한 테스트가 있는 자리만 고르면 모든 변이를 잡았다는 결론이 나온다. 그래서 목록 화면의 이전 결과 가드, 응답 페이지 표시, 캐시 재사용처럼 통과 여부가 확실하지 않은 자리까지 넓혔다.

| 망가뜨린 동작 | 결과 | 관찰한 경계 |
| --- | --- | --- |
| 담긴 상품을 다시 눌러도 제거하지 않음 | 잡힘 | 단위 3건, 통합 2건 |
| 카테고리 변경에서 page를 1로 돌리지 않음 | 잡힘 | 통합 2건 |
| 히스토리 `push`를 `replace`로 변경 | 잡힘 | E2E 2건. 단위와 통합 296건은 통과 |
| 이전 결과를 보는 동안 Next 버튼 가드 제거 | 잡힘 | 통합 1건 |
| 화면의 page 대신 URL 조건의 page를 표시 | 잡힘 | 통합 2건 |
| `keepPreviousData` 제거 | 잡힘 | 통합 3건 |
| `staleTime: 30_000`을 `0`으로 변경 | 살아남음 | 요청 횟수를 보는 테스트가 없음 |
| 총 페이지의 최소 1 보정 제거 | 살아남음 | 0건에서는 페이지 이동 영역이 렌더되지 않음 |
| HTTP 500 재시도 제외 | 잡힘 | 단위 2건 |
| 검색어 parser의 `trim` 제거 | 잡힘 | 단위 1건, 통합 1건 |

두 생존 변이는 같은 방식으로 다룰 수 없었다.

`staleTime`을 0으로 바꿔도 목록은 똑같이 보인다. 달라지는 것은 이미 본 조건으로 돌아왔을 때 나가는 요청의 수다. 화면 결과만 단언한 통합 테스트 296개는 불필요한 재요청을 구별하지 못했다. MSW 서버의 `request:start` 이벤트로 요청을 세는 테스트를 넣었다.

```ts
expect(requestedCategories).toEqual(['all', 'digital'])
```

같은 변이를 다시 넣자 이 테스트가 실패했다. 여기서 한 번 잘못 갔다. 요청 수를 세는 테스트를 쓰면서 응답까지 직접 만들려고 `_pages`에서 `app/api/_data`를 가져왔다. 커밋 훅이 역방향 의존이라며 막았다.

처음에는 테스트 하나 때문에 막혔다고 생각했다. import를 다시 보니 훅이 맞았다. 알고 싶은 것은 응답 내용이 아니라 요청 수인데, 필요하지도 않은 상위 레이어를 끌어오고 있었다. 기본 MSW 핸들러는 그대로 두고 `request:start` 이벤트만 관찰했다. 테스트용 응답 구현도 함께 사라졌다.

총 페이지의 최소 1 보정은 경우가 달랐다. `totalCount`가 0일 때만 계산 결과가 달라지지만 목록이 0건이면 페이지 이동 영역을 그리지 않는다. 사용자가 관찰할 수 없는 방어 코드다. 보정을 억지로 통과시키는 테스트 대신 “0건에서는 페이지 이동 영역이 없다”는 전제를 고정했다. 이 분기가 바뀌어 보정에 도달할 수 있게 되면 먼저 깨질 테스트다.

살아남은 변이의 수만 세면 두 경우가 모두 구멍이다. 관찰 가능한 동작을 놓친 것인지, 실행 경로에 닿지 않는 동등 변이인지 구분해야 다음 테스트가 정해진다.

## 손으로 고른 열 곳도 편향돼 있었다

수동 실험 10건 중 2건이 살아남자 처음보다는 안심했다. 쉬운 곳만 고른 결과는 아니라고 생각했다. 그래도 사람이 고른 열 곳이라는 사실은 바뀌지 않았다. 단위 규칙이 있는 7개 파일에 Stryker를 걸자 변이 158개 중 11개가 살아남았다. 예상보다 많았다.

| 실행 | 죽임 | 살아남음 | 점수 | 시간 |
| --- | ---: | ---: | ---: | ---: |
| 첫 실행 | 147 | 11 | 93.04% | 1분 10초 |
| 테스트 보강 후 | 157 | 1 | 99.37% | 1분 7초 |

도구가 찾은 빈 곳은 세 종류였다. `hasNonDefaultFilters`는 네 조건을 조합한 입력만 검증했다. 검색어, 카테고리, 정렬, 페이지만 기본값에서 벗어난 입력을 각각 넣자 조건식의 네 절을 따로 지킬 수 있었다.

찜 버튼은 더 직접적인 구멍이었다. 장바구니 버튼은 `aria-pressed`를 확인했지만 찜 버튼은 헤더 개수만 봤다. `useIsInWishlist`가 통째로 `undefined`가 되어도 테스트가 통과했다. 버튼 자신의 눌림 상태를 단언하자 같은 모양의 두 기능이 서로 다른 깊이로 검증되던 비대칭이 사라졌다.

검색어 parser는 읽을 때의 `trim`만 확인했다. URL로 쓸 때의 `serialize`에서 `trim`을 없애도 살아남았다. 쓰기 방향 입력을 추가해 양쪽 경계를 고정했다.

보강 뒤 99.37%가 나왔을 때는 솔직히 100%를 만들고 싶었다. 숫자가 하나 남아 있으면 덜 끝난 것처럼 보이기 때문이다. 하지만 Stryker를 `pnpm check`에 넣지는 않았다. 실행마다 67~73초가 드는 것도 부담이지만 더 걸리는 점은 따로 있었다. 변이 점수는 합격선이 아니다. 살아남은 변이가 실제 구멍인지, 도달할 수 없는 코드인지, 다른 하네스가 맡은 경계인지 읽어야 한다. 게이트에 점수를 걸면 이 판단은 금세 100%를 만드는 작업으로 바뀐다.

그래서 단위 로직을 크게 바꿀 때 꺼내 보는 도구로 남겼다. 매번 돌리지 않는 선택이 처음에는 후퇴처럼 느껴졌지만, 100%를 목표로 두지 않으려면 실행 위치도 달라야 했다.

## 0.63%는 왜 죽이지 않았나

보강 뒤 남은 변이는 하나였다.

```ts
searchParams.ts:65   { history: 'push' } -> {}
```

nuqs 2.9.0에서 빈 옵션은 `replace`로 해석된다. 수동 실험에서 이미 확인한 히스토리 회귀와 같은 변경이다. 그래도 같은 결과라고 추론하는 데서 멈추지 않았다. 변이를 넣은 production build 위에서 두 하네스를 다시 돌렸다.

| 하네스 | 결과 |
| --- | --- |
| Vitest 단위와 통합 | 304건 전부 통과 |
| Playwright E2E | 뒤로가기와 앞으로가기 2건 실패 |

Stryker는 Vitest만 실행한다. 브라우저 히스토리에서만 관찰되는 값을 죽이려면 변이 하나마다 production build와 Playwright를 붙여야 한다. 99.37%의 나머지는 단위 테스트의 누락이 아니라 Stryker 실행 범위 밖에 있었다. E2E 두 건이 그 경계를 실제로 지키므로 변이는 남겨 뒀다.

처음에는 테스트 피라미드에서 몇 개를 어느 층에 놓을지가 문제라고 생각했다. 열 번 망가뜨리고 158개 변이를 돌린 뒤에는 기준이 조금 달라졌다. 순수 규칙은 단위 테스트로 내리고 여러 코드의 배선은 통합 테스트에서 본다. 실제 브라우저가 결과를 결정하면 E2E까지 올린다. 변이 테스트는 그 배치가 놓친 자리를 찾지만 모든 층을 대신하지 않는다.

최종 게이트에는 node와 jsdom, Storybook, lint, typecheck, build, E2E가 들어간다. Stryker는 그 밖에서 살아남은 변이를 해석한다. 가장 오래 남은 숫자는 99.37%가 아니었다. 히스토리를 덮어썼을 때도 초록이던 304개와, 그제야 멈춘 브라우저 테스트 두 개였다.
