실행 환경에서만 클래스를 못 찾는다

javac가 만든 클래스 파일을 JVM이 로드한다. 연결 단계에서 바이트코드를 검증하고 정적 필드를 준비하며 심볼을 해석한다. 해석은 사용 시점까지 미룰 수 있다. 초기화 단계가 되면 클래스 초기화 코드를 실행한다. 장애 조사에서는 jar tf로 배포 파일을 열고 실제 프로세스의 실행 인자, 클래스패스·모듈 경로, 요청한 로더를 확인한다.

패키지와 클래스 이름이 같은데 왜 형변환이 실패할까?

런타임 클래스의 정체성에는 이진 이름과 정의 로더가 함께 들어간다. 서로 다른 플러그인이 같은 바이트를 직접 정의하면 두 Class 객체가 생긴다. 양쪽의 getClassLoader()와 클래스 객체의 동일성을 출력한다. 공용 인터페이스를 부모 로더에서 한 번 정의하면 그 타입으로 양쪽을 연결할 수 있다.

플러그인만 자식 우선으로 읽고 싶다면 어디에 경계를 둘까?

자식 우선 탐색은 플러그인 전용 패키지로 좁히고 플랫폼 클래스와 공용 API는 부모에 위임한다. 중복 공용 JAR과 패키지 충돌을 검사한다. 모듈의 접근 경계도 확인한다. 로더를 분리해도 신뢰하지 않는 코드의 파일·네트워크 권한은 남으므로 그런 코드는 별도 프로세스와 OS 권한으로 격리한다.

클래스를 못 찾았다는 두 오류는 어떤 순서로 조사할까?

Class.forName처럼 이름으로 요청한 로더가 대상을 찾지 못하면 ClassNotFoundException을 볼 수 있다. 이미 컴파일된 코드의 의존 클래스를 JVM이 구하지 못하면 NoClassDefFoundError가 날 수 있다. 후자는 초기화에 이미 실패한 클래스를 다시 써도 나온다. 최초 예외의 원인 체인과 -Xlog:class+load=info의 로딩 출처를 배포 JAR과 대조한다.

상수 풀에 메서드 이름이 있는데 실행하면 왜 NoSuchMethodError가 날까?

호출자에 기록된 소유 타입·메서드 이름·디스크립터를 javap -v로 찾고, 런타임에 로드된 라이브러리에서 같은 조합을 찾는다. 동적 연결 시 그 메서드를 해석할 수 없으면 오류가 드러난다. 해석 시점은 구현에 따라 달라질 수 있으므로 모든 참조가 시작 시점에 유효했다고 단정하지 않는다.

두 클래스의 초기화가 서로를 기다리면 어떤 일이 생길까?

같은 스레드가 이미 초기화 중인 클래스를 다시 요청하면 재귀 초기화는 돌아오며 아직 기본값인 필드가 보일 수 있다. 두 스레드가 각기 다른 클래스의 초기화를 시작하고 상대의 완료를 기다리면 교착될 수 있다. 최초 실패가 일반 예외면 ExceptionInInitializerError, 뒤의 사용자는 NoClassDefFoundError를 볼 수 있다. 교착은 스레드 덤프로, 실패는 최초 원인 로그로 조사한다.

힙은 남았는데 G1의 정지가 길어진다

스레드의 프레임은 호출의 복귀와 함께 빠진다. 힙의 객체는 GC 루트로부터의 도달 가능성으로 수명을 판단한다. G1은 힙을 리전으로 나눠 젊은 리전과 선택한 오래된 리전에서 살아 있는 객체를 옮긴다.

오래된 배열 한 칸에 새 객체를 넣으면 GC는 어떻게 알까?

참조 쓰기 뒤에 카드 단위로 변경 영역을 표시하고, 기억 집합은 선택된 리전 바깥에서 들어오는 참조를 찾을 범위를 좁힌다. 카드는 더 넓은 구간을 나타내므로 스캔 비용이 남는다. 동시 마킹 중 이전 참조를 보존하는 SATB 쓰기 전 장벽은 다른 목적을 가진다.

혼합 수집에 오래된 리전을 전부 넣지 않는 이유는?

리전의 회수 가능 공간이 커도 살아 있는 객체를 복사하고 바깥 참조를 스캔하는 데 시간이 든다. G1은 이전 측정에서 예상한 비용과 정지 예산을 바탕으로 후보를 고른다. 정지 목표는 예측에 쓰는 값이므로 시간을 넘긴 수집이 실제로 있었는지 로그로 확인한다.

힙 여유량이 충분한데 큰 배열을 만들지 못할 수 있을까?

HotSpot G1에서 객체 전체 크기가 리전 절반을 넘으면 대형 객체 경로로 갈 수 있다. 필요한 만큼 리전이 연속해야 하며 마지막 리전의 꼬리 공간도 남는다. 객체 헤더·정렬을 포함해 크기를 계산하고, 실제 리전 크기와 Humongous regions의 전후 개수, 할당 시점의 GC 원인을 함께 본다. 대형 리전 개수 하나만으로 단편화를 확정할 수는 없다.

플러그인을 내려도 메타스페이스가 줄지 않으면 어떻게 재현할까?

자식 로더로 같은 플러그인을 반복 로딩한 뒤 부모 쪽 목록에 로더를 보관한 실행과 목록을 비운 실행을 비교한다. -Xlog:class+unload와 로더별 클래스 수를 보고, 의심되는 로더는 힙 덤프에서 GC 루트까지 참조 경로를 추적한다. 로더가 회수 가능해지는 시점과 메타스페이스 사용량·RSS가 떨어지는 시점은 다를 수 있다.

요청 객체 대부분이 예상보다 오래 살아남으면 수집기 선택도 바꿀까?

먼저 할당률, GC 후 생존량과 승격, old 점유율의 장기 추세를 본다. 높은 생존율은 옮길 바이트를 늘린다. 같은 부하·힙·CPU 예산에서 수집기별 처리량, CPU와 요청 p99, GC 정지 분포를 함께 비교한 뒤 목표에 맞는 쪽을 고른다. 계속 늘어나는 참조를 누수로 유지하는 프로그램은 먼저 참조 경로부터 고친다.

같은 코드인데 첫 요청과 이후 요청의 비용이 다르다

HotSpot의 인터프리터가 바이트코드를 실행하는 동안 얻은 정보를 JIT가 활용한다. 컴파일된 코드가 있다고 지금 실행 중인 프레임까지 자동으로 바뀌는 것은 아니다. 메서드의 새 호출과 이미 반복 중인 호출을 나눠 설명해 보자.

메서드를 딱 한 번 불러도 긴 루프가 컴파일될까?

메서드 진입용 코드는 이후 호출에서 처음부터 쓴다. OSR은 이미 돌아가는 호출의 특정 바이트코드 위치에서 지역 변수 등의 현재 상태를 받아 컴파일된 코드로 이어간다. PrintCompilation의 %와 @ BCI를 보고 일반 진입 컴파일과 구별한다.

인라인한 호출에 처음 보는 타입이 들어오면?

타입 가드가 다른 구현으로 분기할 수 있다. 해당 경로가 uncommon trap으로 이어지면 HotSpot은 최적화 코드의 디버그 정보에 기록된 바이트코드 위치·값·인라인 호출 범위를 이용해 논리적 인터프리터 프레임을 복원할 수 있다. 모든 타입 변화가 역최적화를 발생시키는 것은 아니다. 실제 가드 실패와 컴파일 ID를 연결한다.

몇 번 호출하면 C2가 컴파일할까?

호출 횟수와 루프가 되돌아가는 횟수가 서로 다른 신호다. 컴파일 레벨, 프로파일 수집 상태, 옵션과 컴파일 큐 부하에 따라 정책이 달라진다. JDK 버전과 옵션을 기록하고 실행 로그에서 대상 메서드·레벨·OSR 여부를 확인한다. 고정된 ‘2만 번’으로 예측할 수 없다.

워밍업 도중 발생한 지연을 JIT 탓이라고 말하려면?

타임스탬프가 있는 요청 표본, 컴파일 이벤트, GC·세이프포인트, OS의 CPU 대기·스로틀링을 같은 구간에 맞춘다. 컴파일러 스레드가 CPU를 쓴 시간 전체가 애플리케이션의 정지 시간은 아니다. 새 JVM을 여러 번 띄워 시작 구간과 정상 상태를 따로 비교한다. 동시에 기록된 이벤트만으로 한 원인에 밀리초를 배분하지 않는다.

같은 JAR과 AOT 바이너리를 다른 서버에 배포하면?

JAR은 클래스 파일 버전과 의존성이 맞는 대상 플랫폼 JVM이 필요하다. 네이티브 실행 파일은 빌드 시 선택한 OS·ISA·ABI 조건과 맞아야 한다. AOT는 시작 전에 컴파일 비용을 지불한다. JIT는 실행 중 비용을 쓰고 실제로 관찰한 경로를 특화할 수 있다. 사전 훈련 프로파일을 쓰는 AOT도 있으므로 첫 요청·정상 처리량·메모리를 따로 비교한다.

배열 복사를 한 번 호출하면 얼마나 드나

서로 다른 배열에 고정 폭 원소 n개를 실제로 옮기면 Θ(n)의 일을 한다. 명령 하나가 여러 원소를 처리해도 길이가 커지면 옮길 데이터는 늘어난다.

int[]와 Object[]를 옮기는 CPU 작업이 같을까?

기본형은 런타임 원소 타입이 맞아야 한다. 참조형은 목적지 타입에 모두 들어가는지 배열 타입으로 증명하거나 원소별로 검사한다. G1에는 참조 범위를 덮는 쓰기 장벽도 있다. 참조 원소의 타입이 맞지 않아 실패하면 첫 실패 원소 앞까지는 이미 복사됐고 그 뒤의 목적지 값은 그대로다.

같은 배열에서 한 칸 오른쪽으로 밀 때 원본을 어떻게 보존할까?

쓰기 전에 원본을 읽을 수 있는 순서가 필요하다. 끝에서 시작하거나 짧은 구간 전체를 레지스터에 먼저 읽어도 된다. Java가 보장하는 것은 임시 배열을 거친 것과 같은 결과다. 공개 실험에서 16바이트 ARM64 경로는 두 번 읽은 뒤 두 번 쓴다.

JNI로 보내면 오히려 손해가 되는 경우는?

짧은 작업을 원소마다 호출하면 Java↔native 전환 비용을 여러 번 낸다. 배열 접근 API가 사본을 돌려주면 가져오기와 반납 정책에 따른 추가 복사가 생긴다. 같은 작업의 빈 호출, 일괄 호출, 순수 Java 경로를 비교하고 isCopy를 기록한다. VM intrinsic으로 바뀐 System.arraycopy를 일반 JNI 호출의 기준값으로 그대로 쓸 수는 없다.

바이트코드에서 invokestatic을 찾으면 intrinsic 적용까지 확인한 걸까?

그 명령은 클래스 파일의 호출 지점을 알려 준다. 같은 BCI의 C2 로그에서 intrinsic 결정을 찾고 호출자 기계어가 가리키는 복사 루틴을 같은 프로세스의 주소와 대조한다. intrinsic을 끈 새 JVM에서 같은 결과가 나오면서 호출 지점이 달라지는지도 확인한다.

배열 길이와 캐시 재사용 효과를 어떻게 분리해서 잴까?

먼저 한 번에 복사하는 길이를 고정하고 같은 두 배열을 재사용하거나 여러 버퍼를 순환한다. 다음 실험에서 작업 집합 조건을 맞춘 채 길이를 바꾼다. 할당·데이터 검사·워밍업은 측정 구간에서 분리한다. 시간 차이는 관찰값이다. 특정 캐시 계층의 미스로 귀속하려면 하드웨어 카운터와 작업 집합 조건도 확인해야 한다.

독립적인 외부 조회 두 건을 기다린다

두 조회 사이에 데이터 의존성이 없다면 동시에 시작해 완료를 합칠 수 있다. 성공 경로 지연은 느린 쪽의 지연에 대기·합성 비용을 더한 값에 가까워진다. CPU가 이미 포화됐거나 두 호출이 같은 작은 연결 풀을 기다리면 이득이 줄어든다.

JDK 25에서 가상 스레드가 운반 스레드를 붙잡고 있는지 어떻게 볼까?

JDK 24부터 모니터 안에서 블로킹한다는 이유만으로 고정되지 않는다. native·외부 함수 경계 등 남아 있는 경우를 조사하고, JFR의 jdk.VirtualThreadPinned와 스택·지연을 함께 살핀다. 이벤트가 없다는 사실만으로 모든 네이티브 대기가 사라졌다고 추론하지 않는다.

외부 서비스의 ‘동시에 4개, 초당 10회’ 계약을 어떻게 지킬까?

진행 중인 요청은 세마포어 등으로 제한하고 작업 종료 때 허가를 반환한다. 시작 빈도는 별도 rate limiter로 제한한다. 토큰 버킷은 버스트를 허용하므로 ‘어떤 1초 구간에도 10회 이하’라는 계약에는 슬라이딩 윈도 같은 방식을 쓴다. 대기 중에도 요청의 전체 기한이 흐른다.

한 호출이 실패하면 이미 시작한 나머지를 어떻게 정리할까?

두 결과가 모두 필수면 전체 기한을 정하고 첫 실패나 기한 만료 시 형제 작업과 미완료 HTTP 호출에 취소를 전파한다. 호출별 타임아웃을 함께 설정한다. 취소는 협력적이며 서버가 이미 끝낸 동작을 되돌리지 않는다. 부분 결과가 허용되는 제품이면 누락을 명시하고 늦은 응답 처리 정책을 정한다.

p99가 긴 서비스의 연결 풀과 동시성 상한을 어떻게 잡을까?

안정된 구간에서 평균 동시 작업 수는 완료율과 평균 체류시간의 곱이다. 대기가 포함되는 경계를 먼저 고른다. p99를 이 식의 평균에 넣지 않는다. 하위 서비스별 한도와 HTTP/1.1 연결 수 또는 HTTP/2 스트림 한도를 확인한 뒤 부하를 올리며 획득 대기, 꼬리 지연, 오류율 중 무엇이 먼저 악화되는지 본다.

플랫폼 스레드, 가상 스레드, 코루틴 중 무엇을 고를까?

소수의 작업이나 CPU 연산은 코어 수에 맞춘 플랫폼 스레드 풀이 단순하다. 대량의 블로킹 I/O를 기존 동기 Java 코드로 처리할 때는 가상 스레드가 유리할 수 있다. Kotlin의 중단 가능 API에서는 코루틴이 중단 지점의 상태를 저장하고 나중에 dispatcher에서 재개한다. 일반 블로킹 함수를 호출하면 그 스레드는 점유된다. 중단과 재개에는 상태 보관과 스케줄링 비용이 남는다. OS 스레드 전환에서는 커널이 레지스터와 스택 포인터 등의 실행 문맥을 교체하고 캐시 지역성도 달라질 수 있다. 코루틴 한 번의 중단이 OS 스레드 전환 한 번을 뜻하지는 않는다.
