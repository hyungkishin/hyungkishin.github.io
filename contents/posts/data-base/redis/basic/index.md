쿠폰 발급 워커 두 개가 같은 회원의 요청을 동시에 집어 들면 어느 쪽이 발급해야 할까. 하나의 Redis 인스턴스에 회원별 락을 두는 예를 생각해 보자. 락에는 두 가지 시간이 얽혀 있다. Redis 키가 살아 있는 시간과 워커가 실제 발급을 마칠 때까지 걸리는 시간이다.

## 락 획득과 만료를 한 명령에 담는다

여기서 쿠폰은 행사당 회원 한 명에게 한 장만 발급한다. 두 워커는 같은 행사와 회원에 대해 같은 키를 쓴다. 아래에서 `token-A`는 워커 A가 이번 획득 시도에만 쓰는 값이다. 실제로는 시도할 때마다 새로운 무작위 값을 만든다.

```text
SET lock:coupon:summer:member-42 token-A NX PX 5000
```

`NX`는 키가 없을 때만 저장하고, `PX 5000`은 키가 5초 뒤에 만료되도록 한다. 먼저 저장한 워커는 `OK`를 받고 발급을 시작한다. 그사이에 다른 워커가 자기 토큰으로 같은 키를 요청하면 null 응답을 받으므로 발급을 시작하지 않는다. 획득과 만료 설정 사이에 프로세스가 죽어 무기한 락이 남는 틈도 없다. [Redis SET 명령](https://redis.io/docs/latest/commands/set/)

## 락을 풀기 전에 소유자를 비교한다

A가 멈춘 사이 5초가 지나면 B는 같은 키에 자신의 토큰을 저장할 수 있다. 뒤늦게 돌아온 A가 키 이름만 보고 삭제하면 B의 락이 사라진다. 해제할 때는 키의 값이 자신의 토큰과 같을 때만 삭제한다.

```lua
if redis.call("GET", KEYS[1]) ~= ARGV[1] then
    return 0
end
return redis.call("DEL", KEYS[1])
```

이 Lua 스크립트에서 `KEYS[1]`은 락 키, `ARGV[1]`은 획득할 때 넣은 토큰이다. Redis는 값 비교와 삭제를 한 스크립트 안에서 실행한다. 키가 이미 만료됐거나 B의 토큰이 들어 있으면 A의 해제 요청은 0을 반환한다. [Redis의 단일 인스턴스 락과 해제](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/#correct-implementation-with-a-single-instance)

## 발급 건수가 한 건인지는 DB에서 결정한다

A가 쿠폰을 저장하기 직전에 오래 멈췄다고 하자. 락은 만료되고 B가 새 락을 얻어 쿠폰을 발급한다. 그 직후 A가 다시 움직이면 A도 저장을 시도한다. 토큰 비교는 B의 락을 지켜 주지만 이미 실행 중인 A의 DB 쓰기까지 멈추지는 않는다.

이 예에서는 쿠폰 발급 테이블의 `(행사 ID, 회원 ID)` 조합에 유니크 제약을 둔다. 두 워커가 같은 발급 건을 넣으려 해도 DB에는 한 행만 남는다. 중복 요청을 받은 쪽은 이미 저장된 발급 건을 읽어 돌려줄 수 있다. Redis 락은 한꺼번에 몰린 작업을 줄이고, 발급의 최종 판단은 쿠폰이 기록되는 곳에서 내린다.
